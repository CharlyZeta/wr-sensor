# CONTRACT: ingestion escala horizontalmente sin perder orden por sensor ni transiciones de severidad (consumo particionado por sensorId)

## Intent
Hoy `ingestion-service` consume de **una sola cola** (`queue.sensor.lecturas`, binding
`lectura.#` sobre el exchange topic `sensor.lecturas`). No hay particionamiento por
`sensorId`, así que no existe paralelismo real por partición y escalar el servicio
(`--scale ingestion-service=3`) convierte a las instancias en **competing consumers** de la
misma cola. Eso rompe dos garantías: (a) el orden relativo de las lecturas de un mismo sensor
y (b) el **estado en memoria** `ultimaSeveridad` (FEAT-0011) que decide si se emite alerta —
repartido entre procesos, deja de detectar transiciones y **se pierden alertas reales**.
Este fix introduce particionamiento determinista por `sensorId` (consistent-hash exchange +
binding exchange-to-exchange, **sin cambios en el publisher**), con número de particiones
configurable y con afinidad sensor → partición → instancia, que es lo que hace consistente el
estado en memoria sin moverlo a Redis.

## Reproduction Steps
1. Levantar el stack con **más de una instancia** consumidora:
   `docker compose up -d --build --scale ingestion-service=3` (la cola es única y las tres
   instancias declaran la misma binding `lectura.#` → competing consumers).
2. Publicar **3 lecturas consecutivas del mismo sensor** que produzcan las severidades
   `NORMAL` → `ALTO` → `NORMAL` (valores dentro del rango físico de FIX-0004, p. ej. vía
   `data-simulator` o `rabbitmqadmin publish exchange=sensor.lecturas routing_key=lectura.<id>`).
3. Consultar el resultado:
   `SELECT id, sensor_id, severidad_anterior, severidad_nueva FROM outbox_alerta ORDER BY id;`
   y `SELECT ts, valor, severidad FROM lectura WHERE sensor_id = :id ORDER BY ts;`
4. Repetir el paso 2 con **una sola instancia** y comparar el conteo de eventos.

## Current Behavior
- Paso 3: con 3 instancias el conteo de filas de `outbox_alerta` para ese sensor es **0 o
  menor a 2** (esperado 2). Cada instancia tiene su propio `Map<UUID, Severidad>
  ultimaSeveridad` (`IngestorLecturas.java:41`), y `cambio = anterior != null && anterior !=
  severidad` (línea 95): la instancia que recibe la lectura casi nunca tiene el estado previo,
  así que **la transición no se emite**. Con 1 instancia (paso 4) sí se emiten las 2.
- Paso 3 (orden): el orden de procesamiento por sensor no está garantizado con competing
  consumers: dos lecturas del mismo sensor pueden procesarse en paralelo en instancias
  distintas, y el orden de inserción en `lectura`/`outbox_alerta` deja de reflejar el orden de
  emisión.
- No existe ninguna noción de partición: `ingestion.lecturas.queue` es un nombre escalar
  (`application.yml:24-28`, `IngestionProperties.Lecturas:27`), el consumer declara una cola
  y una binding (`LecturasRabbitConsumer.java:52-68`) y consume con `qos(1)` + `flatMap`
  (líneas 72-76).
- El publisher ya publica con routing key estable por sensor (`lectura.{sensorId}`,
  `RabbitLecturaPublisher.java:40`) — hoy desaprovechada para particionar.

## Expected Behavior
- Las lecturas de un mismo `sensorId` se enrutan **siempre a la misma partición** (mientras el
  número de particiones no cambie) y esa partición la consume **exactamente una instancia**
  (BR-001/BR-005) → afinidad sensor → partición → instancia.
- Dentro de una partición las lecturas se procesan **secuencialmente y en orden de llegada**
  (1 consumer por partición, `qos = 1`, sin concurrencia intra-partición) — BR-002.
- La partición se resuelve en el broker con un exchange **`x-consistent-hash`**
  (`sensor.lecturas.part`) alimentado por un binding **exchange-to-exchange** desde
  `sensor.lecturas` (topic, RK `lectura.#`), con `N` colas `queue.sensor.lecturas.p{i}` y peso
  de binding `"1"`. El **publisher no cambia** y `query-api`/`alerting-service` conservan sus
  colas actuales — BR-003.
- `N` (**default 4**) y el subconjunto de particiones que consume cada instancia son
  **configurables por entorno**, nunca hardcodeados; cada instancia declara la topología
  completa pero consume solo sus particiones asignadas — BR-004/BR-005.
- Como consecuencia de la afinidad, el estado en memoria `ultimaSeveridad` vuelve a ser
  correcto: **ninguna transición de severidad se pierde por escalar** (mismo resultado con 1 o
  con 3 instancias) — BR-007.
- Cada cola de partición preserva las garantías ya contratadas: ack manual post-persistencia,
  `x-dead-letter-exchange` hacia la DLX común, idempotencia por clave de FIX-0003 — BR-006.
- Si hay particiones sin consumer asignado, se loguea WARN al arrancar y sus mensajes quedan
  en cola (lag observable, sin pérdida) — BR-008. Si la topología no se puede declarar
  (p. ej. exchange type no soportado por el broker), la instancia registra ERROR y **no** arranca
  el consumo: nunca se degrada en silencio a "consumir sin particionar" — BR-009.

## Use Case
**Actor:** plataforma / operador de despliegue (y, de forma indirecta, la operación de
monitoreo que recibe alertas).
**Goal:** aumentar el throughput de ingesta agregando instancias de `ingestion-service` sin
perder orden por sensor ni transiciones de severidad.

### Main Flow
1. Se habilita en el broker el exchange type `rabbitmq_consistent_hash_exchange` y la
   instancia arranca con `ingestion.particiones.total = 4` y `asignadas = [0,1,2,3]`.
2. Al arrancar, la instancia declara la topología completa: exchange topic `sensor.lecturas`,
   exchange `sensor.lecturas.part` (`x-consistent-hash`), las `N` colas
   `queue.sensor.lecturas.p{i}` (con su `x-dead-letter-exchange`), el binding e2e
   `sensor.lecturas → sensor.lecturas.part` con RK `lectura.#`, y los `N` bindings de cola con
   peso `"1"` hacia la DLX/DLQ.
3. `data-simulator` publica en `sensor.lecturas` con RK `lectura.{sensorId}` (sin cambios).
4. El exchange topic reenvía al consistent-hash exchange, que hashea la routing key y enruta
   cada mensaje a **una** de las `N` colas.
5. La instancia dueña de esa partición consume el mensaje con ack manual: ventana temporal →
   sensor → rango físico (FIX-0004) → severidad contra `ultimaSeveridad` → persistencia
   atómica en `lectura`/`lectura_procesada` (+ `outbox_alerta` si hay transición), y recién
   entonces ack.
6. Escalar a 3 instancias (`asignadas = [0]`, `[1]`, `[2,3]`, por ejemplo) mantiene la
   afinidad: cada sensor sigue cayendo en su partición y en la misma instancia, con lo que
   `ultimaSeveridad` es coherente y las transiciones se emiten igual que con una instancia.

### Alternative Flows
- AF-01: `asignadas` contiene un índice fuera de `[0, total-1]` (o `total` inconsistente) → la
  instancia falla el arranque con error de configuración explícito y **no** consume nada.
- AF-02: `total` ≤ 0 o `asignadas` vacío → error de configuración explícito, sin consumo.
- AF-03: una instancia muere y su partición queda sin consumer → los mensajes permanecen en
  `queue.sensor.lecturas.p{i}` (no van a DLQ, no se pierden) y se procesan cuando la instancia
  vuelve; el resto de las particiones sigue operando.
- AF-04: redelivery del mismo mensaje por fallo post-persistencia y pre-ack → la clave de
  idempotencia (FIX-0003) descarta el duplicado: una sola fila en `lectura` y **sin** re-emitir
  la transición de severidad.

## Business Rules
- BR-001: Afinidad por sensor. Mientras `ingestion.particiones.total` no cambie, todas las
  lecturas de un mismo `sensorId` se enrutan a la misma partición (`queue.sensor.lecturas.p{i}`)
  y esa partición es consumida por exactamente una instancia. Consecuencia verificable: el
  conteo y el orden de los eventos de severidad de un sensor no dependen del número de
  instancias.
- BR-002: Orden intra-partición. Cada partición tiene **un** consumer (una conexión de consumo)
  con `qos = 1` y procesamiento **secuencial** (sin `flatMap` concurrente dentro de la
  partición): las lecturas de un sensor se procesan en el orden en que fueron encoladas. Subir
  `qos` o paralelizar intra-partición viola esta regla.
- BR-003: Topología de particionamiento. Exchange `x-consistent-hash`
  (`ingestion.particiones.exchange`, default `sensor.lecturas.part`) con binding
  exchange-to-exchange desde el exchange topic `sensor.lecturas` con RK `lectura.#`; `N` colas
  `ingestion.particiones.patron` (`queue.sensor.lecturas.p{i}`, sufijo `{i}`) bindeadas con
  routing key de peso `"1"`. El publisher (`data-simulator`) **no** se modifica; las colas de
  `query-api` y `alerting-service` **no** se ven afectadas.
- BR-004: Configurabilidad. `ingestion.particiones.total` (default **4**) y
  `ingestion.particiones.asignadas` (default = todas las particiones) son configurables por
  `application.yml` **y** por variable de entorno, con default documentado. Prohibido
  hardcodear `N` ni los índices en el código.
- BR-005: Declarar todo, consumir lo propio. Cada instancia declara la topología **completa**
  (idempotente) para que el orden de arranque no importe, pero **consume únicamente** las
  particiones de `asignadas`: no puede haber dos consumers concurrentes sobre la misma cola de
  partición.
- BR-006: Garantías por partición. Cada cola de partición conserva lo contratado en FEAT-0011 y
  FIX-0003: ack manual **después** de persistir, `x-dead-letter-exchange` = DLX común y DLQ
  compartida, header `x-rechazo` en los rechazos, y dedupe por clave de idempotencia (un
  redelivery o un reproceso no duplica filas ni eventos).
- BR-007: Consistencia del estado en memoria. La afinidad sensor → partición → instancia es la
  que hace correcto `ultimaSeveridad` (FEAT-0011): con cualquier cantidad de instancias dentro
  del rango de particiones, no se pierde ninguna transición de severidad (mismo resultado que
  con una sola instancia). Este Contract **no** mueve ese estado a almacenamiento compartido.
- BR-008: Visibilidad de particiones sin consumer. Si la instancia arranca con
  `asignadas.size() < total`, se registra un log **WARN** indicando las particiones sin
  consumer; sus mensajes quedan en cola (lag observable) y no se pierden ni se descartan.
- BR-009: Fail-fast de topología. Si los exchanges/colas/bindings no se pueden declarar
  (broker sin el exchange type `x-consistent-hash`, permisos, config inválida), la instancia
  registra **ERROR** y **no** inicia el consumo: se prohíbe degradar silenciosamente a un
  consumo no particionado. Excepción: la DLQ/DLX (comportamiento tolerante ya existente).
- BR-010: Documentación operativa. La topología nueva (exchanges, colas, particiones,
  asignación por instancia, procedimiento de cambio de `total` con reinicio coordinado y
  drenaje de la cola anterior `queue.sensor.lecturas`) queda en `docs/ARQUITECTURA.md` y
  `docs/RUNBOOK.md`.

## Acceptance Criteria
- AC-001 (BR-003): GIVEN una instancia con `total = 4` WHEN arranca contra un broker con el
  exchange type habilitado THEN existen el exchange `sensor.lecturas.part`
  (`x-consistent-hash`), el binding e2e `sensor.lecturas → sensor.lecturas.part` (`lectura.#`)
  y las 4 colas `queue.sensor.lecturas.p0..p3` bindeadas con peso `"1"`, y las colas de
  `query-api`/`alerting-service` siguen existiendo y bindeadas a `sensor.lecturas`.
- AC-002 (BR-001, BR-002, BR-007): GIVEN `total = 4` WHEN se publican 3 lecturas consecutivas
  del mismo sensor con severidades `NORMAL → ALTO → NORMAL` **con 1 instancia** y **con 3
  instancias** (`asignadas = [0]`, `[1]`, `[2,3]`) THEN en ambos casos hay exactamente **2**
  filas en `outbox_alerta` para ese sensor, con `id` creciente correspondiente a las
  transiciones `NORMAL→ALTO` y `ALTO→NORMAL`, y 3 filas en `lectura` con severidades
  `NORMAL, ALTO, NORMAL` en orden de `ts`. *(Hoy falla con 3 instancias: 0 transiciones.)*
- AC-003 (BR-004): GIVEN un broker limpio y la misma imagen WHEN se cambia
  `ingestion.particiones.total` a `2` por variable de entorno (sin recompilar) THEN las colas
  de partición declaradas son exactamente `queue.sensor.lecturas.p0` y `p1` (no se declaran
  `p2`/`p3`) y **todas** las lecturas publicadas terminan en `p0` o `p1`.
- AC-004 (BR-005): GIVEN `total = 4` y dos instancias con `asignadas = [0]` y `[1]` WHEN ambas
  arrancan THEN las 4 colas de partición existen (topología completa declarada por cada una),
  `p0` y `p1` tienen **exactamente 1** consumer cada una, `p2` y `p3` tienen **0** consumers, y
  ninguna cola tiene 2 consumers concurrentes.
- AC-005 (BR-006): GIVEN una lectura con payload inválido enrutada a `queue.sensor.lecturas.p1`
  WHEN la instancia la procesa THEN el mensaje aparece en la DLQ con header `x-rechazo`; y
  GIVEN un redelivery con la misma clave de idempotencia THEN `lectura` conserva **una sola**
  fila y no se genera un segundo evento de severidad.
- AC-006 (BR-008): GIVEN `total = 4` y una instancia con `asignadas = [0]` WHEN arranca THEN
  se emite un log WARN con las particiones `1,2,3` sin consumer y los mensajes publicados para
  esas particiones permanecen en sus colas (visible por la profundidad de cola), sin
  descartarse.
- AC-007 (BR-009): GIVEN un broker donde el exchange `x-consistent-hash` no puede declararse
  WHEN la instancia intenta iniciar el consumo THEN se registra un log ERROR y **no** queda
  ningún consumer activo (no se consume sin particionar).
- AC-008 (BR-010): GIVEN el estado final del work item WHEN se revisan `docs/ARQUITECTURA.md` y
  `docs/RUNBOOK.md` THEN documentan la topología particionada, la asignación de particiones por
  instancia, el escalado (`--scale` con `asignadas` por instancia) y el procedimiento de
  cambio de `total` con drenaje de la cola anterior.

- **Topología RabbitMQ** (nueva): exchange `sensor.lecturas.part` (tipo `x-consistent-hash`),
  binding e2e `sensor.lecturas → sensor.lecturas.part` (`lectura.#`), colas
  `queue.sensor.lecturas.p{i}` (`i = 0..N-1`), bindings de peso `"1"`; DLX/DLQ sin cambios.

- **`IngestionProperties`**: nueva sección `ingestion.particiones {total, asignadas, exchange,
  patron}`; `Lecturas.queue` pasa a ser derivada del patrón.
- **`LecturasRabbitConsumer`**: declara la topología completa y consume el subconjunto
  asignado; 1 consumer por partición con `qos = 1` y procesamiento secuencial.
- **`IngestorLecturas`**: sin cambios de lógica (sigue con `ultimaSeveridad` en memoria); su
  corrección pasa a depender de la afinidad (BR-007).
- **`application.yml`** de `ingestion-service` y **`docker-compose.yml`** (habilitación del
  plugin `rabbitmq_consistent_hash_exchange` en el broker e instancias con `asignadas`).
- **ITs** de `ingestion-service`: contenedor RabbitMQ con el plugin habilitado.
- **`docs/ARQUITECTURA.md`**, **`docs/RUNBOOK.md`**: topología y procedimiento operativo.

## Fuera de alcance
- **Rebalanceo en caliente** al cambiar `total`: asume reinicio coordinado (el anillo del
  consistent hash se recalcula y remapea claves). Sin rebalanceo automático ni doble lectura de
  la topología vieja y la nueva.
- **Persistir `ultimaSeveridad`** (Redis o tabla): decisión humana 2026-09-11 — este Contract
  se apoya en la afinidad y se limita a particionar. Queda como ítem de backlog propio (es lo
  que además desbloquearía escalar `alerting-service`).
- **`alerting-service` y `query-api`**: siguen con un consumer por cola. Riesgo documentado:
  `GestorAlertas` mantiene estado en memoria por sensor (ventana de histéresis), así que
  escalarlos horizontalmente tendría el mismo problema de afinidad → Contract separado.
- **Uniformidad estricta del reparto entre particiones**: el consistent hash garantiza
  *afinidad*, no reparto uniforme; con pocos `sensorId` distintos el sesgo hacia algunas
  particiones es esperable (documentado en el plugin) y **no** es un criterio de aceptación.
- Métricas/paneles de lag por partición (Prometheus/Grafana) más allá del WARN de BR-008.
- Cambios en el payload del evento (incluido `sequence`/`eventId` como campos obligatorios):
  el contrato vigente del payload es el de FEAT-0010 y FIX-0003.

> Notas de implementación (no spec, no generan AC): el stack actual soporta la solución sin
> dependencias nuevas — `Sender.bindExchange(BindingSpecification.binding()
> .exchangeFrom("sensor.lecturas").exchangeTo("sensor.lecturas.part").routingKey("lectura.#"))`,
> `ExchangeSpecification.exchange("sensor.lecturas.part").type("x-consistent-hash")
> .durable(true)` y bindings de cola con `routingKey("1")` (reactor-rabbitmq 1.5.6). El plugin
> `rabbitmq_consistent_hash_exchange` viene incluido en la distribución de RabbitMQ pero **no**
> está habilitado por defecto en `rabbitmq:3.13-management-alpine`: se habilita vía
> `enabled_plugins` (imagen/compose) y en los ITs con
> `RabbitMQContainer.withPluginsEnabled("rabbitmq_consistent_hash_exchange")`. Los índices se
> toman de `asignadas` (default `[0..total-1]`); la declaración de topología es idempotente, por
> lo que el orden de arranque de las instancias es irrelevante. Medición del escalado real:
> publicar con `--scale` y comparar profundidad de colas y conteo de filas.

## Ambiguity Log
- [x] Mecanismo de particionamiento: RESUELTO (humano 2026-09-11) = **consistent-hash exchange
      con binding exchange-to-exchange** y `N` colas fijas con peso `"1"`. Alternativas
      descartadas: (B) sufijo de partición en la routing key desde `data-simulator` (viola
      BR-002 del doc original: obliga a cambiar el publisher y convierte el rebalanceo en
      redeploy del simulador); (C) `x-single-active-consumer` (da orden pero un único consumer
      activo: no hay escalado horizontal real). Requiere, sí, habilitar el plugin del broker
      en infra e ITs.
- [x] Número de particiones default: RESUELTO (humano 2026-09-11) = **4 particiones**
      (configurable, default documentado). Rationale: cubre las 3 instancias del escenario de
      escalado con margen, y deja la uniformidad como best-effort (la garantía es afinidad).
      Alternativas descartadas: 6 ("una por sensor inicial": rígido al agregar sensores),
      3 (sin margen).
- [x] Alcance sobre `ultimaSeveridad`: RESUELTO (humano 2026-09-11) = **fuera de alcance**;
      la afinidad sensor → partición → instancia hace correcto el estado en memoria. La
      persistencia del estado de severidad se registra como backlog propio.
- [x] Migración de `queue.sensor.lecturas`: RESUELTO (orquestador 2026-09-11, sujeto a
      confirmación en HO-Gate) = **retirar la cola vieja** y aceptar reproceso de sus mensajes
      pendientes (la idempotencia de FIX-0003 lo tolera), con drenaje documentado en RUNBOOK.
      Alternativa descartada: convivencia temporal de ambas topologías con doble consumo
      (duplicaría trabajo y exigiría dedupe adicional).
- [x] Cita de dependencia del doc original: RESUELTO (orquestador 2026-09-11) = el `eventId` y
      la idempotencia provienen de `contracts/FIX-0003` (no de `FIX-0002`, que fue el
      `valorLectura` hardcodeado en alerting); el campo `sequence` **no existe** en el payload
      vigente y no se usa en ningún AC de este Contract.
