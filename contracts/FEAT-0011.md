## Intent
Crear el microservicio `ingestion-service` (services/ingestion-service): consume el
exchange `sensor.lecturas` (payload FEAT-0010 BR-002:
`{sensorId, timestamp, valor, unidadMedida}`), valida, calcula la **severidad**
(`NORMAL`/`WARNING`/`CRITICAL`) contra los rangos del sensor, persiste la lectura en
TimescaleDB (hypertable `lectura`) y publica `AlertaEvento` a `sensor.alertas`
(topic, key `alerta.{severidad}`) cuando corresponde. Sin API HTTP (solo consumer).
Fuente spec: §3, §4 Lectura/AlertaEvento, §5 (bandas + histéresis), §6 (RabbitMQ),
§9.2 (TimescaleDB raw 90 días), §9.3 (retry/DLQ configurables), stack.md.

## Use Case
**Actor:** Sistema (consumidor automático del exchange `sensor.lecturas`)
**Goal:** Incorporar cada lectura válida al histórico y derivar eventos de severidad

### Main Flow
1. `sensor.lecturas` entrega una lectura con key `lectura.{sensorId}` (payload
   FEAT-0010).
2. El servicio valida el payload (campos y tipos) y resuelve la **configuración del
   sensor** (rangos/histéresis/unidad) para `sensorId`.
3. Calcula la severidad de la lectura contra las bandas del sensor, persiste la
   lectura cruda en la hypertable `lectura` y — si corresponde (ver decisiones) —
   publica `AlertaEvento` a `sensor.alertas` (key `alerta.{severidad}`).
4. Consumo exitoso → ack; fallo de procesamiento → reintentos configurables y luego
   DLQ (`messaging.retry.*`, `messaging.dead-letter.exchange` — nunca hardcodeado).

### Alternative Flows
- AF-01: Payload malformado o campos inválidos (sensorId/timestamp/valor/unidad
  ausentes o de tipo incorrecto) → lectura descartada con log, **sin** ack de
  error → va a DLQ tras reintentos (configurable).
- AF-02: Sensor desconocido para `sensorId` (sin config resuelta) → lectura a DLQ
  (no hay forma de evaluar severidad ni persistir con sentido) tras reintentos.
- AF-03: Sensor en estado `INACTIVO` → la lectura se **rechaza** (el sensor está
  dado de baja, FEAT-0005): a DLQ con motivo `SENSOR_INACTIVE`.
- AF-04: Configuración del sensor no disponible transitoriamente (sensor-registry
  caído/error de red, si se usa REST) → reintento con backoff; al agotar → DLQ.
- AF-05: `timestamp` de la lectura fuera de la ventana de aceptación
  (configurable, ej. ±5 min contra el reloj) → lectura descartada a DLQ
  (`TIMESTAMP_OUT_OF_WINDOW`).

## Business Rules
- BR-001: Contrato de entrada: payload JSON de `sensor.lecturas` con
  `sensorId` (UUID), `timestamp` (instant), `valor` (decimal finito), `unidadMedida`
  ∈ {METROS, CENTIMETROS}. Payload inválido → error de procesamiento (AF-01).
- BR-002: La severidad de una lectura se evalúa contra los **rangos del sensor**
  (cadena inclusiva normal ⊆ warning ⊆ critical): dentro de `rangoNormal` →
  `NORMAL`; fuera de normal pero dentro de `rangoWarning` → `WARNING`; en otro
  caso → `CRITICAL`. (Base de la histéresis: ver Ambiguity Log.)
- BR-003: La lectura válida se persiste **siempre** en la hypertable `lectura`
  (TimescaleDB): `sensor_id`, `ts` (columna de partición), `valor`, `unidad_medida`,
  `severidad`. Sin upsert: cada lectura es un nuevo row.
- BR-004: `AlertaEvento` (payload `{sensorId, timestamp, valorLectura,
  severidadAnterior, severidadNueva, cruceHisteresis}`) se publica en
  `sensor.alertas` con key `alerta.{severidadNueva}` según las decisiones de abajo;
  nunca se publica un evento para una lectura rechazada.
- BR-005: Consumo con **ack después de persistir** (at-least-once); reintentos y
  DLQ configurados vía `application.yml` (`messaging.retry.*`,
  `messaging.dead-letter.exchange`), nunca hardcodeados (spec §9.3).
- BR-006: La cola de consumo se declara con DLQ propia y exchange `sensor.lecturas`
  durable; binding key `lectura.*`. Sin API HTTP en este servicio (stack: solo
  consumo por mensajería).
- BR-007: Stack reactivo: consumer con **Reactor RabbitMQ** y R2DBC (cero
  bloqueante, cero JPA); persistencia y publicación encadenadas sin `.block()`.
- BR-008: Tolerancia a fallos de TimescaleDB: si la persistencia falla, la lectura
  NO se ackea (reintentos → DLQ); el consumo no se detiene.

## Acceptance Criteria
- AC-001: GIVEN una lectura válida de un sensor ACTIVO con valor dentro de
  `rangoNormal` y una fila previa del mismo sensor en severidad `NORMAL`
  WHEN el servicio procesa la lectura
  THEN persiste la lectura con `severidad=NORMAL` y NO publica `AlertaEvento` (sin
  cambio).
- AC-002: GIVEN una lectura válida con valor fuera de `rangoNormal` (en
  `rangoWarning`) y severidad previa `NORMAL`
  WHEN el servicio procesa la lectura
  THEN persiste con `severidad=WARNING` y publica `AlertaEvento` con
  `severidadNueva=WARNING` y key `alerta.WARNING` (subida inmediata).
- AC-003: GIVEN una lectura con valor fuera de `rangoWarning` (en
  `rangoCritical`/fuera) y previa `WARNING`
  WHEN el servicio procesa la lectura
  THEN persiste con `severidad=CRITICAL` y publica evento key `alerta.CRITICAL`.
- AC-004: GIVEN una lectura malformada (p. ej. sin `valor` o `sensorId` no UUID)
  WHEN el servicio la procesa
  THEN no persiste nada y el mensaje termina en la DLQ tras los reintentos
  configurados (verificado en el IT).
- AC-005: GIVEN una lectura de un sensor desconocido
  WHEN el servicio la procesa
  THEN termina en la DLQ (motivo `SENSOR_UNKNOWN` en el header/body de DLQ).
- AC-006: GIVEN una lectura de un sensor `INACTIVO`
  WHEN el servicio la procesa
  THEN termina en la DLQ (motivo `SENSOR_INACTIVE`) sin persistir.
- AC-007: GIVEN N lecturas válidas de sensores ACTIVOS
  WHEN el servicio las procesa
  THEN la hypertable `lectura` contiene exactamente N filas (cuantificable en el IT
  por consulta) y `sensor.alertas` recibió los eventos esperados por los cambios de
  severidad.
- AC-008: GIVEN una lectura con `timestamp` muy lejano al presente (fuera de la
  ventana configurable)
  WHEN el servicio la procesa
  THEN no persiste y termina en la DLQ (motivo `TIMESTAMP_OUT_OF_WINDOW`).

## Entities Affected
- Lectura (owner pasa a ingestion-service desde FEAT-0010): se persiste cruda
  (nueva tabla/hypertable `lectura` en TimescaleDB, spec §4/§9.2). Retención raw 90
  días + compresión desde día 8 = config de TimescaleDB (ver notas), no de código.
- AlertaEvento (evento saliente, spec §4): consumido por FEAT-0012 alerting-service.
- Sensor: **solo lectura de config** (rangos/histéresis/estado/unidad) — owner
  sigue siendo sensor-registry; ver Ambiguity Log sobre la fuente.

> Notas de implementación (no spec, no generan AC): módulo Maven nuevo standalone
> (como FEAT-0010); `domain` puro (Lectura, AlertaEvento, evaluador de bandas sin
> Spring), `application` (procesar lectura: validar → resolver sensor → evaluar →
> persistir → publicar) y `infrastructure` (Reactor RabbitMQ Receiver + R2DBC +
> TimescaleDB). Schema: `schema.sql` (CREATE TABLE + índice) y una migración
> idempotente al arranque que convierte a hypertable
> (`create_hypertable('lectura','ts', if_not_exists=>true)`) — R2DBC no ejecuta
> multi-sentencias, se corre vía DatabaseClient. Imagen TimescaleDB para IT
> (timescale/timescaledb). Windows de aceptación y retry en `application.yml`.

## Ambiguity Log

      **REST a sensor-registry** (`GET /api/sensores/{id}`, requiere credencial
      VIEWER configurada; cache en memoria) — fuente única, sin duplicar rangos.
      Alternativa = espejo local de los 6 sensores (drift posible). Requiere
      decisión humana.
- [x] Publicación de `AlertaEvento`: RESUELTO (humano 2026-09-09) = evento simple por cambio; histéresis en FEAT-0012
      **ingestion publica evento en cada cambio de severidad** (subida inmediata;
      degradación sin margen) y **FEAT-0012 alerting aplica la histéresis** de
      degradación antes de notificar (consistente con ESTADO-PROYECTO FEAT-0012).
      Alternativa = ingestion aplica histéresis completa (estado por sensor en
      memoria/Redis) y publica solo cambios confirmados (spec §5 literal). Requiere
      decisión humana.
- [x] Estado "última severidad": RESUELTO (humano 2026-09-09) = en memoria
      **en memoria** (single instance dev; se pierde al reiniciar → próximo evento
      se publica contra el estado fresco). Alternativa = Redis. Requiere decisión
      humana (menor).
- [x] Persistencia: RESUELTO (humano 2026-09-09) = **TimescaleDB real** (hypertable)
      Postgres simple en v1 con estructura lista para TimescaleDB. Propuesta =
      **TimescaleDB real** (spec §9.2 es decisión resuelta). Requiere decisión
      humana (entorno/IT).
