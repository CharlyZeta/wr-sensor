# CONTRACT: GlobalErrorHandler emite class name en vez de domain code estable en path de validación estructural
# ID: FIX-0001
# Status: RESOLVED (Loop completado 2026-08-12 — 1/1 ✅)
# Mode: LOOP

## Intent
`GlobalErrorHandler.deriveCodeFromBinding` (ruta de `WebExchangeBindException`,
i.e. Bean Validation en el bind del controller) devuelve
`*.class.getSimpleName()` — p. ej. `"InvalidHisteresisException"` — en lugar
del `code` estable del dominio (`"SENSOR_INVALID_HISTERESIS"`) que el resto del
handler y los AC-XXX de `FEAT-0001` asumen. La ruta de dominio (`SensorException`,
`handleDomain`) sí devuelve el code correcto; solo el path estructural está
roto. Esto rompe consistencia entre rutas y hará fallar cualquier AC futuro
que valide una falla de Bean Validation (los AC-XXX actuales llegan al servicio
y nunca tocan este path).

## Reproduction Steps
1. `POST /api/sensores` con `Authorization: Bearer <JWT rol ADMIN>`
2. Body con `tipo` = `""` (string vacío) — `@NotBlank` en `SensorRequest.tipo`
   dispara `WebExchangeBindException` en el bind, antes de llegar al servicio.
   Resto de campos válidos (incluido `codigo`, `nombre`, los 3 rangos).
3. Inspeccionar `response.body.code`.

(Análogamente con `histeresis` ausente, `latitud` faltante, `codigo` vacío,
`rangoNormal.min` null, etc.: cualquier campo mapeado en el `switch` dispara
el mismo bug con su `InvalidXxxException` correspondiente.)

## Current Behavior
`response.body.code` es el simple-name de la clase de excepción del dominio:
- `latitud`/`longitud` → `"InvalidCoordinatesException"`
- `histeresis` → `"InvalidHisteresisException"`
- `frecuenciaReporteSegundos` → `"InvalidFrecuenciaException"`
- `estado` → `"InvalidEstadoException"`
- `unidadMedida` → `"InvalidUnidadException"`
- `tipo` → `"InvalidTipoException"`
- `rangoNormal`/`rangoWarning`/`rangoCritical` → `"InvalidRangesException"`
- `codigo` → `"SensorCodeDuplicatedException"`
- otro campo → `"SENSOR_INVALID_REQUEST"` (default — OK).

Tomado de `GlobalErrorHandler.deriveCodeFromBinding`, `services/sensor-registry/src/main/java/com/wrsensor/sensorregistry/infrastructure/adapter/in/web/GlobalErrorHandler.java:62-79`.

## Expected Behavior
`response.body.code` es el `code` estable del dominio para el mismo mapeo de
campo (mismos strings que retorna `SensorException.code()` y que asertan los
AC-XXX del Contract `FEAT-0001`):
- `latitud`/`longitud` → `"SENSOR_INVALID_COORDINATES"`
- `histeresis` → `"SENSOR_INVALID_HISTERESIS"`
- `frecuenciaReporteSegundos` → `"SENSOR_INVALID_FRECUENCIA"`
- `estado` → `"SENSOR_INVALID_ESTADO"`
- `unidadMedida` → `"SENSOR_INVALID_UNIDAD"`
- `tipo` → `"SENSOR_INVALID_TIPO"`
- `rangoNormal`/`rangoWarning`/`rangoCritical` → `"SENSOR_INVALID_RANGES"`
- `codigo` → `"SENSOR_INVALID_REQUEST"` (resolución humana 2026-07-31:
  semánticamente "campo requerido", no "duplicado"; evita mezclar dos
  significados en el mismo code)
- otro campo → `"SENSOR_INVALID_REQUEST"` (default — sin cambio).

El HTTP status sigue siendo `400 BAD REQUEST` (sin cambio).
