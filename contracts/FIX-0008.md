## Intent
La revisión de seguridad encontró que el gateway —el **único** punto de entrada publicado y el futuro
host del SPA— tiene tres problemas que se refuerzan entre sí: (a) **S1**: en `docker-compose.yml` el
servicio `api-gateway` **no recibe `AUTH_JWT_SECRET`**, así que cae al default de desarrollo
(`wrsensor-dev-secret-2026-no-usar-en-prod`, público en el repo); como el gateway es el que valida el
JWT del handshake WebSocket (`FEAT-0008` BR-003), en un despliegue con el secreto rotado **cualquiera
puede forjar un token `ADMIN`/`VIEWER`** con el secreto del repo y abrir los WS de telemetría y de
alertas; (b) **S3**: no existe **ningún header de seguridad** en todo el repositorio (0 coincidencias
de `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`), y al
servir el SPA desde el mismo origen que la API el panel queda sin segunda línea de defensa contra XSS
ni contra clickjacking; (c) **S2/A6**: el catch-all del router responde `404 ROUTE_NOT_FOUND` a
cualquier path no declarado, así que el hosting del SPA no puede funcionar sin tocar el router — y el
fallback, si se implementa ingenuamente ("todo lo que no matchea → `index.html`"), rompe el contrato
de la API y devuelve `200 text/html` a assets inexistentes.
Este work item cierra los tres **antes** de que el SPA se sirva desde el gateway.

## Reproduction Steps
1. Levantar el stack con el secreto rotado: `$env:AUTH_JWT_SECRET = "secreto-real-de-produccion"`;
   `docker compose up -d --build`.
2. Comprobar que el gateway **no** recibió el secreto:
   `docker compose exec api-gateway printenv AUTH_JWT_SECRET` → sin salida (variable ausente), mientras
   `docker compose exec sensor-registry printenv AUTH_JWT_SECRET` → el secreto rotado.
3. Acuñar un JWT HS256 con el secreto **público del repo** y el formato del emisor
   (`"sub":"<uuid>","rol":"ADMIN","iat":n,"exp":n`), y presentarlo en el upgrade del WS:
   `GET /ws/alertas?token=<forjado>` con `Upgrade: websocket`.
4. **Observado hoy:** el handshake se completa (`101`) y el cliente recibe el feed de alertas con rol
   `ADMIN` forjado — el gateway aceptó un token que el `sensor-registry` (con el secreto rotado)
   rechazaría. El mismo token abre `WS /ws/sensores/{id}` (telemetría completa).
5. Comprobar la ausencia de headers: `curl.exe -sS -D - -o NUL http://localhost:8084/` y
   `curl.exe -sS -D - -o NUL http://localhost:8084/api/sensores/resumen -H "Authorization: Bearer $t"`
   → ninguna respuesta trae `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`,
   `X-Frame-Options`/`frame-ancestors` ni `Permissions-Policy`.
6. Comprobar el bloqueo del hosting: con un `index.html` presente en
   `services/api-gateway/src/main/resources/static/`, `curl.exe -i http://localhost:8084/` →
   **`404 ROUTE_NOT_FOUND`** (el catch-all del `RouterFunction` gana sobre el `ResourceWebHandler`).

## Expected Behavior
1. El gateway recibe `AUTH_JWT_SECRET` en `docker-compose.yml` (mismo valor por entorno que el
   registry), y un despliegue **no-dev** con el secreto de desarrollo configurado **no arranca**
   (fail-fast)
   en vez de aceptar tokens forjables.
2. Toda respuesta del gateway (SPA, API y errores) sale con los headers de seguridad configurados, y
   el gateway **no duplica** los valores que vengan del downstream.
3. `GET /` y las rutas del cliente devuelven el índice del SPA, mientras todo `/api/**` no declarado
   sigue siendo `404 ROUTE_NOT_FOUND` en JSON y los assets inexistentes (`/assets/*.js`, `.css`)
   siguen siendo `404` — nunca `200 text/html`.

### Alternative Flows
- AF-01: el secreto del WS no está configurado y el perfil activo **no** es de desarrollo → el
  gateway falla al arrancar con un mensaje explícito (nunca arranca con el default dev en prod).
- AF-02: el perfil activo **es** de desarrollo → se permite el default documentado, con WARN en el
  arranque indicando que los tokens son forjables.
- AF-03: un path de asset con traversal (`/..%2f..%2fapplication.yml`, `/WEB-INF/web.xml`) → `404`
  sin leer nada fuera de `static/` y sin reflejar el path en un cuerpo HTML.
- AF-04: un path de API con traversal o extensión de asset (`/api/loquesea.js`) → sigue siendo el
  `404 ROUTE_NOT_FOUND` de la API (JSON), no el fallback del SPA.
- AF-05: el downstream manda sus propios headers de seguridad → el gateway usa **su** valor
  configurado y no lo duplica (una sola ocurrencia por header en la respuesta).
- AF-06: la lista de orígenes de tiles configurada para el SPA está vacía → la CSP sale con
  `img-src 'self' data:` (sin `*`, sin comodines amplios) y se documenta cómo habilitar un proveedor.

## Business Rules
- BR-001: **El secreto de firma del WS debe ser el mismo en todo el despliegue**: `docker-compose.yml`
  pasa `AUTH_JWT_SECRET` a `api-gateway` (con el mismo default por entorno que el registry) y
  `docker-compose.dev.yml` no lo altera.
- BR-002: **Fail-fast fuera de desarrollo**: si el perfil activo no es `dev`/`local`/`test` y el
  secreto coincide con el default de desarrollo (o está vacío), el gateway **no arranca**; en perfil
  de desarrollo arranca con WARN. La decisión es de configuración (`gateway.ws.jwt-secreto` +
  perfil), no un `if` hardcodeado sobre el valor.
- BR-003: **Headers de seguridad configurables y únicos**: el gateway aplica
  `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `X-Frame-Options: DENY` + `frame-ancestors 'none'`, `Permissions-Policy` y
  `Cross-Origin-Resource-Policy: same-origin` a **toda** respuesta; los valores salen de
  `gateway.seguridad.*` (con default documentado) y **no** se duplican si el downstream ya los mandó.
  HSTS se emite sólo cuando la request llegó por HTTPS (`X-Forwarded-Proto: https`).
- BR-004: **La CSP por default no permite `unsafe-inline` ni `unsafe-eval` en `script-src`**;
  `img-src` incluye sólo `'self'`, `data:` y los orígenes de tiles configurados (nunca `*` ni `https:`
  a secas); `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'self'` y
  `connect-src 'self'` (más orígenes explícitos si se configuran).
- BR-005: **Resolución de estáticos contenida**: los archivos se resuelven siempre dentro de
  `classpath:/static/`; se rechaza cualquier path con `..`, `%2e%2e`, backslash, byte nulo o segmento
  vacío; el handler de fallback **no** lee query ni headers del request para decidir qué servir.
- BR-006: **El fallback del SPA no altera el contrato de la API**: `/api/**` y `/ws/**` conservan su
  comportamiento (404 `ROUTE_NOT_FOUND` / 426 `WS_UPGRADE_REQUIRED` / upgrade autenticado); los paths
  con extensión de asset que no existen devuelven 404 (nunca el índice), y sólo rutas de cliente
  (`/`, `/mapa`, `/sensores/**`, `/login`) devuelven `index.html`.
- BR-007: **Caché explícita**: `index.html` se sirve con `Cache-Control: no-store` y los assets
  versionados por hash (bajo `/assets/`) con cache inmutable de un año; las respuestas de API que
  llevan datos sensibles no se cachean (`no-store`).
- BR-008: **Sin valores hardcodeados**: CSP, headers, rutas de cliente permitidas, orígenes de tiles y
  TTLs de caché viven en `application.yml` con overrides por entorno; ningún valor nuevo en el código.
- BR-009: **Evidencia verificable**: tests del gateway (integración sin Docker) que afirman cada
  header, el rechazo del traversal, el 404 de la API y el índice del SPA; y las comprobaciones de
  `docker compose config`/`printenv` documentadas en el RUNBOOK.

## Ambiguity Log
- [x] ¿Dónde viven los headers de seguridad? RESUELTO (orquestador 2026-09-15, **sujeto a HO-Gate**) =
  **en el gateway** (único punto de entrada y host del SPA), configurables, aplicados a toda respuesta
  y sin duplicar lo que venga del downstream. Alternativa descartada: en cada servicio (cuatro
  configuraciones que se desincronizan y no cubren el SPA).
- [x] ¿Fail-fast o WARN con el secreto de desarrollo? RESUELTO (orquestador 2026-09-15, **sujeto a
  HO-Gate**) = **fail-fast fuera de perfiles de desarrollo** y WARN dentro: un gateway que acepta
  tokens forjables no debe poder arrancar "por accidente" en un entorno real, pero el flujo de
  desarrollo (`docker compose up` sin configurar nada) tiene que seguir funcionando.
- [x] ¿Cómo decide el fallback del SPA? RESUELTO (orquestador 2026-09-15, **sujeto a HO-Gate**) =
  **lista de rutas de cliente (`/`, `/login`, `/mapa`, `/sensores/**`) → `index.html`**; `/api/**` y
  `/ws/**` intactos; cualquier path con extensión de asset inexistente → `404`. Alternativa
  descartada: "todo lo que no matchea → índice" (rompe el 404 de la API y devuelve HTML a un script
  roto) y "aceptar cualquier path sin extensión" (superficie innecesaria).
- [x] ¿La CSP incluye `unsafe-inline` para estilos? RESUELTO (orquestador 2026-09-15, **sujeto a
  HO-Gate**) = **`style-src 'self' 'unsafe-inline'` documentado como excepción** (Leaflet manipula
  atributos `style` y algunos builds de Vite inyectan estilos críticos), pero **`script-src 'self'`
  sin excepciones**: la excepción de estilos no habilita XSS por script, que es el vector que roba el
  token.
- [x] ¿Se agrega `Cross-Origin-Opener-Policy`? RESUELTO (orquestador 2026-09-15, **sujeto a
  HO-Gate**) = **sí** (`same-origin`) junto con `Cross-Origin-Resource-Policy: same-origin`; no se
  agrega `Cross-Origin-Embedder-Policy` (rompería la carga de tiles de terceros sin aportar al caso).
- [x] ¿Qué pasa con los tiles de terceros frente a una CSP estricta? RESUELTO (orquestador
  2026-09-15, **sujeto a HO-Gate**) = el origen de tiles es **configuración**
  (`gateway.seguridad.csp.img-src`, con default `'self' data:` + el origen documentado de OSM) y el
  SPA sigue siendo usable sin tiles (`FEAT-0009` AC-009).
