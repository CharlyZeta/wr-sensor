# Status: DRAFT

# Gate-Mode: EXPRESS

> **Parte 3 de 4 de la serie del frontend** (división aprobada por el humano 2026-09-14). Depende de
> la base de `FEAT-0009` (sesión, cliente API, mapa, tokens de severidad). Es **independiente** de

> **No cambia el backend**: `WS /ws/alertas?token=<jwt>` (`FEAT-0012` + auth de `FEAT-0008`) ya
> publica las alertas confirmadas.

## Intent
El mapa y el detalle muestran estado, pero el operador necesita **enterarse** de lo que cruza umbral
sin quedarse mirando una pantalla: hoy la única forma es tener el WS abierto a mano. Este work item
agrega el **feed de alertas confirmadas en vivo** —alimentado por `WS /ws/alertas`, una sola conexión
por pestaña— con el sensor afectado, la transición de severidad y la hora, un contador de críticas no
leídas y el **refresco del mapa** cuando la severidad de un sensor cambia (con debounce, para no
romper el cupo del gateway).

## Use Case
**Actor:** operador `ADMIN` o `VIEWER` con el SPA abierto.
**Goal:** ver en un solo lugar qué sensores están alertando ahora, con qué severidad y desde cuándo, y
que el mapa refleje ese cambio sin apretar "refrescar".

### Main Flow
1. Al iniciar sesión, el SPA abre **una** conexión a `WS /ws/alertas?token=<jwt>` (independiente de la
   vista que esté mirando el usuario).
2. Llega una alerta confirmada (`{"sensorId","severidadNueva","confirmada":true,"timestamp"}`): el SPA
   la agrega al **feed** (arriba), resuelve el nombre/código del sensor contra la metadata ya cargada
   y muestra la transición de severidad y la hora.
3. El marcador/ítem de ese sensor en el mapa se actualiza con la severidad nueva y, si la alerta es
   `CRITICAL`, se incrementa el **contador de críticas no leídas**.
4. El SPA refresca el resumen del mapa **una sola vez por ráfaga** (debounce configurable) para
   reconciliar con el backend, en lugar de una request por alerta.
5. El usuario abre el feed, ve el detalle de una alerta y puede saltar al sensor; al abrir el feed se
   marcan como leídas (contador a cero).

### Alternative Flows
- AF-01: el WS de alertas se cae → reconexión con **backoff exponencial con jitter** y aviso
  "alertas en vivo pausadas" con la hora de la última alerta; el feed existente no se borra.
- AF-02: el token vence con la conexión abierta → re-login y **una** reconexión, sin duplicar
  conexiones ni perder el feed ya recibido.
- AF-03: llega la misma alerta dos veces o desordenada (reintento del broker) → se deduplica por
  (`sensorId`, `timestamp`, `severidadNueva`) y el feed se ordena por `timestamp` descendente.
- AF-04: el refresco del resumen devuelve `429` → se suspende el refresco automático, se muestra un
  aviso y se reintenta al vencer el `Retry-After` (el feed sigue funcionando).
- AF-05: el sensor de la alerta no está en la metadata cargada (alta reciente o sensor fuera del
  resumen) → el feed muestra el `sensorId` crudo y un enlace que fuerza la recarga del resumen.
- AF-06: el rol es `VIEWER` → el feed es de sólo lectura y no ofrece acciones administrativas.
- AF-07: llega una alerta de bajada de severidad (`severidadNueva` menos grave) → se muestra como
  **normalización** (color/ícono distinto) y **no** cuenta como crítica no leída.
- AF-08: el usuario recarga la página → el feed arranca vacío y el SPA lo dice explícitamente
  ("el historial se pierde al recargar"), porque las alertas no se persisten en el cliente.

## Business Rules
- BR-001: **Una sola conexión de alertas por pestaña** (no una por vista ni una por sensor), abierta
  con el token por query string (`FEAT-0008` BR-003) y cerrada al cerrar sesión. El token no se
  registra ni se muestra.
- BR-002: Reconexión con **backoff exponencial + jitter** configurable y estado visible
  (`conectado`/`reconectando (n)`/`pausado`); un cierre por logout no reconecta.
- BR-003: **Deduplicación por (`sensorId`, `timestamp`, `severidadNueva`)** y orden por `timestamp`
  descendente; el feed está acotado a **N** entradas en memoria (configurable, default 200) para no
  crecer sin límite.
- BR-004: **El refresco del resumen por alerta se agrupa (debounce, default 2 s)** y nunca produce
  más de una request por ráfaga; con `429` se respeta el `Retry-After` y se pausa el refresco
  automático. Se respeta `VITE_RESUMEN_REFRESCO_MS` de `FEAT-0009`.
- BR-005: **El feed es efímero y lo declara**: las alertas viven en memoria (el historial consultable
  está fuera de alcance), así que la UI dice que se pierden al recargar y nunca insinúa persistencia.
- BR-006: **La severidad usa la misma fuente de verdad que el mapa** (`severidad → color/etiqueta` de
  `FEAT-0009` BR-007), y el contador de no leídas cuenta **sólo** transiciones a `WARNING`/`CRITICAL`
  que empeoran la severidad (una normalización no cuenta).
- BR-007: El nombre del sensor se resuelve contra la metadata ya cargada (sin N+1 de sensores): si no
  está, se muestra el `sensorId` y se ofrece recargar; nunca se muestra un nombre inventado.
- BR-008: Accesibilidad: el feed es una lista navegable por teclado, las alertas nuevas se anuncian
  con una región `aria-live` **sin** robar el foco, y la severidad no se comunica sólo por color.
- BR-009: Todo configurable y documentado: tamaño del feed, debounce, backoff, umbral de críticas y
  período de refresco en variables `VITE_*` con default documentado (`RUNBOOK.md`); `ARQUITECTURA.md`
  documenta el flujo de alertas (WS → feed → refresco del resumen) y `API.md` ya documenta el payload.

## Acceptance Criteria
- AC-001 (Main Flow 1/2): GIVEN una sesión activa WHEN el SPA termina de cargar THEN hay exactamente
  una conexión a `/ws/alertas` con el token y el feed muestra su estado.
- AC-002 (Main Flow 2/3): GIVEN el feed abierto WHEN llega una alerta `CRITICAL` de un sensor THEN la
  entrada aparece con el nombre del sensor, la transición de severidad y la hora, y el marcador del
  mapa pasa a `CRITICAL`.
- AC-003 (AF-03, BR-003): GIVEN la misma alerta recibida dos veces y una alerta más antigua WHEN se
  procesan THEN el feed no tiene duplicados y queda ordenado por `timestamp` descendente.
- AC-004 (AF-08, BR-005): GIVEN una página recién cargada WHEN el usuario mira el feed THEN el feed
  está vacío con el aviso de que el historial no se persiste, y no se muestran alertas de sesiones
  anteriores.
- AC-005 (BR-004, AF-04): GIVEN cinco alertas en menos de un segundo WHEN se procesan THEN se dispara
  **una sola** recarga del resumen, y GIVEN un `429` en esa recarga THEN se pausa el refresco
  automático respetando `Retry-After` sin afectar el feed.
- AC-006 (BR-006, AF-07): GIVEN una alerta de normalización (bajada de severidad) WHEN se muestra
  THEN se distingue visualmente y **no** incrementa el contador de críticas no leídas.
- AC-007 (AF-01, BR-002): GIVEN que el WS se cae WHEN pasan los intentos configurados THEN se ve
  `reconectando`/`pausado` con la hora de la última alerta y el feed previo sigue visible.
- AC-008 (AF-02): GIVEN un token vencido con el feed abierto WHEN el WS falla THEN el SPA re-loguea y
  reconecta una sola vez, sin conexiones duplicadas.
- AC-009 (BR-007, AF-05): GIVEN una alerta de un sensor sin metadata cargada WHEN se muestra THEN el
  feed usa el `sensorId` y ofrece recargar el resumen, sin inventar un nombre.
- AC-010 (BR-008): GIVEN una alerta nueva WHEN llega THEN se anuncia por `aria-live` sin mover el foco
  del usuario y el feed es navegable por teclado.
- AC-011 (BR-009): GIVEN los documentos WHEN se revisan THEN el tamaño del feed, el debounce, el
  backoff y el umbral de críticas están en variables `VITE_*` documentadas y ningún valor está
  hardcodeado en los componentes.

  `aria-live`, integración con el mapa (severidad + debounce de refresco).
- **Backend**: **sin cambios**. Se consume `WS /ws/alertas` (`FEAT-0012` + auth de `FEAT-0008`) y
  `GET /api/sensores/resumen` (`FEAT-0008`).

  (flujo de alertas), `README.md`, `REGISTRO-SDD.md`, `ESTADO-SDD.md`, `ESTADO-PROYECTO.md`,
  `CHANGELOG.md`.
