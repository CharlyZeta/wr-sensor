> Origen: `docs/FIX-0005-gateway-rate-limiting.md` (backlog), revisado en Gate y **promocionado
> como FEAT-0007**: agrega un componente nuevo (no es un bugfix). La serie de `contracts/` es la
> autoritativa (FEAT-0001..0006 y 0010..0013 usados; próximo FEAT libre = 0007). El nombre del
> componente es **`api-gateway`** para no confundirlo con el `ingestion-gateway` de dispositivos
> que menciona la spec §9.3 (concepto distinto: entrada de sensores reales, no de clientes HTTP).

## Intent
Hoy los servicios expuestos (`sensor-registry` :8080, `query-api` :8082, `alerting-service`
:8083 y `data-simulator` :8081) se publican **directo al host**, sin capa intermedia: no hay
punto de entrada único, no hay protección contra fuerza bruta en `POST /api/auth/login`, no hay
límite de consumo en los endpoints de lectura y no hay un lugar donde generar correlación para
el logging. Se crea el microservicio **`api-gateway`** (WebFlux, reactivo, hexagonal, sin
dependencias nuevas) que enruta REST y WebSocket hacia los servicios internos, aplica **rate
limiting configurable por ruta y por IP de origen**, devuelve errores de dominio
(`429`/`502`/`504`/`404` con `{"code","message"}`) y garantiza un `X-Correlation-Id` por
request. Con el gateway adelante, los servicios dejan de publicar puertos al host (sólo el
gateway lo hace) y el acceso directo para debug queda en un override de compose explícito.

## Use Case
**Actor:** Cliente de la plataforma (dashboard/web, usuario autenticado o anónimo en login) y
operador que despliega el stack.
**Goal:** Un único punto de entrada que enrute REST y WS a los servicios internos, frene el
abuso (fuerza bruta y ráfagas) con respuestas claras y trazables, sin exponer los servicios
internos al host.

### Main Flow
1. El stack arranca con `docker compose up`: **sólo `api-gateway` publica puerto al host**
   (`8084:8084`); `sensor-registry`, `query-api`, `alerting-service`, `data-simulator` e
   `ingestion-service` quedan accesibles únicamente por la red interna (DNS de Compose).
2. Un cliente hace `GET /api/sensores` contra el gateway: éste resuelve la ruta por el patrón
   **más específico** (la tabla de rutas es configurable), aplica el límite de su clase
   (`lectura`), y si hay cupo proxya con `WebClient` a `sensor-registry:8080`, preservando
   método, query string, body, `Authorization` y agregando `X-Forwarded-For`/`X-Forwarded-Proto`
   con el `X-Correlation-Id` (propagado si el cliente lo envió, generado si no).
3. La respuesta del downstream vuelve al cliente con su status y headers, **más** el
   `X-Correlation-Id` y los headers de cupo (`X-RateLimit-Limit`, `X-RateLimit-Remaining`). El
   gateway registra una línea de log con método, ruta, status, duración, IP y correlationId.
4. `GET /api/sensores/{id}/lecturas` (y `/actual`) se enrutan a `query-api:8082` — no a
   `sensor-registry` — porque la ruta con patrón más específico gana sobre `/api/sensores/**`.
5. `POST /api/auth/login` se enruta a `sensor-registry` con la clase de límite **`login`**
   (la más estricta): superado el cupo, el gateway responde `429` con `Retry-After` y
   **no** reenvía la petición al downstream.
6. Un cliente abre `ws://<host>:8084/ws/alertas` (o `/ws/sensores/{id}`): el gateway completa
   el handshake contra `alerting-service:8083` (o `query-api:8082`), y luego retransmite los
   frames de texto en ambos sentidos hasta que cualquiera de los dos lados cierre.

### Alternative Flows
- AF-01: Ruta inexistente (`/api/desconocido`, `/api/simulador/estado`) → `404`
  `ROUTE_NOT_FOUND` sin intentar proxy ni buscar un destino por defecto.
- AF-02: Cupo agotado en una ruta → `429` `RATE_LIMIT_EXCEEDED` + `Retry-After` (segundos,
  ≥ 1) + `X-RateLimit-Remaining: 0`; la petición **no** llega al downstream. Otro cliente con
  otra IP de origen sigue operando con su propio cupo.
- AF-03: Downstream inalcanzable (conexión rechazada/DNS) → `502` `UPSTREAM_UNAVAILABLE`;
  downstream que no responde dentro del timeout de la ruta → `504` `UPSTREAM_TIMEOUT`. Nunca
  `500` crudo, nunca un stacktrace en el body.
- AF-04: `X-Correlation-Id` presente pero vacío o con caracteres inválidos (más de 64 chars o
  no imprimibles) → se descarta y se genera uno nuevo (no se propaga basura al downstream).
- AF-05: El downstream cierra el WS (o falla el handshake) → el gateway cierra el lado cliente
  con el mismo status/close code y libera la sesión (sin conexiones colgadas ni fuga de
  recursos); si el upgrade lo pide un cliente y el downstream no está, responde `502`.
- AF-06: Un cliente envía `X-Forwarded-For` falso intentando evadir el límite → por default
  (`gateway.rate-limit.confiar-forwarded-for: false`) el gateway usa la IP del peer y el
  header del cliente se descarta.

## Business Rules
- BR-001: Existe un único componente de entrada (`api-gateway`, :8084) que enruta REST y WS a
  `sensor-registry` (:8080), `query-api` (:8082) y `alerting-service` (:8083). Las rutas se
  declaran en configuración (`gateway.rutas`), con **validación de solapamiento**: la ruta que
  gana es la de patrón más específico y el arranque falla si dos rutas con la misma
  especificidad apuntan a destinos distintos.
- BR-002: La tabla de rutas debe cubrir de forma explícita y verificable: `/api/auth/**` →
  registry; `/api/sensores` y `/api/sensores/{id}` (GET/PUT/DELETE y subrutas no asignadas a
  otro servicio) → registry; `/api/sensores/{id}/lecturas` y `/api/sensores/{id}/actual` →
  query-api; `/ws/alertas` → alerting; `/ws/sensores/**` → query-api. Sin comodín «todo a un
  destino» ni fallback silencioso.
- BR-003: `POST /api/auth/login` tiene su **propia clase de límite**, más estricta que el resto,
  orientada a mitigar fuerza bruta de credenciales; el cupo se cuenta **por IP de origen**.
- BR-004: Los endpoints de lectura (`GET /api/sensores*` y las lecturas de `query-api`) usan la
  clase `lectura`; cualquier otra ruta usa la clase `default`. Los tres valores
  (**10 / 120 / 300 peticiones por 60 s**, con burst **10 / 60 / 100**) y el upgrade WS
  (**30/60 s**, burst 30) son **defaults documentados y configurables**, nunca hardcodeados.
- BR-005: Algoritmo **token bucket** por clave (**clase de límite + IP de origen**), con `burst`
  como tamaño del balde y recarga continua a `peticiones/ventana`; la IP por default es la del
  **peer** (`confiar-forwarded-for: false`), porque el gateway es el primer salto.
- BR-006: Al superar el límite: `429`, body `{"code":"RATE_LIMIT_EXCEEDED","message":…}`,
  header **`Retry-After`** en segundos (entero ≥ 1, calculado desde el próximo token
  disponible) y `X-RateLimit-Limit`/`X-RateLimit-Remaining`. Nunca un timeout silencioso.
- BR-007: Los contadores de claves inactivas se liberan (`gateway.rate-limit.expiracion-segundos`,
  default 300): la memoria del rate limiter no crece sin límite con IPs que ya no aparecen.
- BR-008: **Correlación**: toda petición llega al downstream con un `X-Correlation-Id` — el del
  cliente si es válido, uno generado (UUID) si no — y ese valor se refleja en la respuesta y en
  la línea de log del gateway (`método ruta status duración IP correlationId`). El gateway no
  genera tracing distribuido (fuera de alcance).
- BR-009: **Errores de dominio, nunca crudos**: ruta inexistente → `404 ROUTE_NOT_FOUND`;
  downstream inalcanzable → `502 UPSTREAM_UNAVAILABLE`; timeout → `504 UPSTREAM_TIMEOUT`. Los
  timeouts son configurables por ruta (`gateway.rutas.<id>.timeout-ms`, default 10000) y la
  respuesta de error es siempre `{"code","message"}` (convención de `docs/API.md`), sin
  stacktraces ni detalles internos del downstream.
- BR-010: **Higiene de proxy**: se eliminan los headers hop-by-hop (`Connection`, `Keep-Alive`,
  `Transfer-Encoding`, `TE`, `Trailer`, `Upgrade`, `Proxy-*`) y el `Host` original; se agregan
  `X-Forwarded-For` (IP del peer), `X-Forwarded-Proto` y `X-Forwarded-Host`; `Authorization` se
  propaga intacto (el gateway **no** autentica ni reemplaza el JWT de `sensor-registry`).
- BR-011: **WS tunelado**: se soportan `/ws/alertas` → alerting y `/ws/sensores/**` → query-api
  (path preservado), retransmitiendo frames de texto en ambos sentidos, con cierre propagado en
  ambos lados. El gateway **no** agrega autenticación al handshake (los WS de `alerting` y
  `query-api` no la tienen hoy): brecha conocida, registrada en «Fuera de alcance» y en ADR.
- BR-012: **Exposición**: sólo el gateway publica puerto al host. `sensor-registry`,
  `query-api`, `alerting-service`, `data-simulator` e `ingestion-service` no publican puertos
  (deja de violarse BR-06 del doc origen: hoy `data-simulator` publica `8081:8081`). El acceso
  directo para desarrollo se habilita explícitamente con `docker-compose.dev.yml`
  (`docker compose -f docker-compose.yml -f docker-compose.dev.yml up`), documentado en el
  RUNBOOK. Los puertos de infraestructura (RabbitMQ, Postgres, Timescale, Redis) siguen
  publicados por ser herramientas de desarrollo y no servicios de la aplicación.
- BR-013: Stack y estilo: WebFlux reactivo, hexagonal estricto (dominio puro para tabla de rutas,
  token bucket y correlación; infraestructura para el proxy `WebClient`, el puente WS y la
  configuración), cero dependencias nuevas, cero bloqueante, `application.yml` con defaults
  documentados y overrides por entorno.

## Acceptance Criteria
- AC-001 (BR-001, BR-012): GIVEN `docker-compose.yml` WHEN se inspecciona su configuración THEN
  **sólo** `api-gateway` declara `ports:` entre los servicios de aplicación (registry,
  simulator, ingestion, alerting y query-api no publican puertos) y `docker-compose.dev.yml`
  existe y los republica; y GIVEN el gateway arrancado con downstreams stub WHEN se hace
  `GET /api/sensores` THEN la respuesta es `200` con el payload del registry y el stub registró
  **una** invocación.
- AC-002 (BR-002): GIVEN el gateway WHEN se pide `GET /api/sensores/{id}` THEN llega al
  `sensor-registry`, y WHEN se pide `GET /api/sensores/{id}/lecturas` y
  `GET /api/sensores/{id}/actual` THEN llegan al `query-api` (mismo prefijo, ruta más específica
  gana); ambos casos verificados contra downstreams stub que registran lo recibido.
- AC-003 (BR-011): GIVEN un downstream WS de prueba WHEN un cliente abre
  `ws://localhost:8084/ws/alertas` a través del gateway THEN el handshake se completa, un frame
  enviado por el downstream llega al cliente, un frame del cliente llega al downstream y al
  cerrar el downstream el cliente ve el cierre.
- AC-004 (BR-003, BR-006): GIVEN `login` = 10 peticiones/60 s WHEN se hacen 10 `POST
  /api/auth/login` por el gateway (misma IP) THEN las 10 llegan al downstream, y WHEN se hace la
  11ª THEN la respuesta es `429` con `{"code":"RATE_LIMIT_EXCEEDED"}`, `Retry-After` entero ≥ 1
  y el downstream **no** recibió esa petición (10 invocaciones contadas).
- AC-005 (BR-004, BR-005): GIVEN `lectura` = 120/60 s WHEN se hacen 120 `GET /api/sensores`
  desde una IP THEN todas se resuelven normalmente (status del downstream, sin 429) y la 121ª
  devuelve `429`; y GIVEN otra IP de origen WHEN pide `GET /api/sensores` THEN se le permite
  (el cupo es por IP, no global).
- AC-006 (BR-008): GIVEN una request **sin** `X-Correlation-Id` WHEN pasa por el gateway THEN el
  downstream recibe un `X-Correlation-Id` no vacío y la respuesta al cliente trae el mismo valor;
  GIVEN una request **con** `X-Correlation-Id: abc-123` THEN downstream y respuesta conservan
  `abc-123`; y el log del gateway incluye ese id junto al status.
- AC-007 (BR-008, AF-04): GIVEN `X-Correlation-Id` inválido (vacío o de 200 caracteres) WHEN
  pasa por el gateway THEN se descarta y se genera uno nuevo (el downstream nunca recibe el
  valor inválido).
- AC-008 (BR-001, AF-01): GIVEN una ruta no declarada (`/api/desconocido`) WHEN se invoca THEN
  la respuesta es `404` con `{"code":"ROUTE_NOT_FOUND"}` y ningún downstream recibió tráfico.
- AC-009 (BR-009, AF-03): GIVEN un destino caído WHEN se invoca su ruta THEN la respuesta
  es `502` `UPSTREAM_UNAVAILABLE`; GIVEN un destino que demora más que `timeout-ms` THEN la
  respuesta es `504` `UPSTREAM_TIMEOUT`. En ambos casos el body es `{"code","message"}` y nunca
  `500`.
- AC-010 (BR-010): GIVEN una request con headers hop-by-hop (`Connection`, `Transfer-Encoding`)
  y un `Host` propio WHEN pasa por el gateway THEN el downstream no recibe esos headers, sí
  recibe `X-Forwarded-For`/`X-Forwarded-Proto` con el peer real, y el `Authorization` original
  intacto.
- AC-011 (BR-004, BR-013): GIVEN la misma imagen WHEN se cambia la clase `login` a 3
  peticiones/60 s por configuración/entorno (sin recompilar) THEN la 4ª petición ya devuelve
  `429`; y los valores efectivos de las cuatro clases quedan expuestos por configuración con sus
  defaults documentados.
- AC-012 (BR-007): GIVEN el rate limiter con `expiracion-segundos` corto WHEN transcurre el
  tiempo sin tráfico de una IP THEN su entrada se elimina (el número de claves activas vuelve a
  0), verificable con reloj inyectado y sin esperar la ventana real.
- AC-013 (BR-013, AF-06): GIVEN una request con `X-Forwarded-For: 9.9.9.9` (spoof) WHEN se agota
  el cupo de la IP real THEN sigue devolviendo `429` (el header del cliente se ignora por
  default), y con `confiar-forwarded-for: true` el comportamiento cambia a usar el header
  (verificado con la config explícita).

## Fuera de alcance
- **Autenticación de WebSocket**: `/ws/alertas` y `/ws/sensores/*` no validan token hoy
  (`SimpleUrlHandlerMapping` sin auth en `alerting-service` y `query-api`). El gateway tunela el
  upgrade sin agregar auth: **brecha conocida y documentada** (ADR-0016), a resolver en un work
  item propio junto con el cliente del frontend.
- **Autenticación/autorización en el gateway**: no se valida JWT ni se reemplaza el de
  `sensor-registry`; sólo se propaga `Authorization`.
- **Rate limiting distribuido** (varias instancias del gateway con contador compartido en Redis):
  v1 es **por instancia, en memoria**. Redis ya está en el compose para una evolución futura.
- **TLS/HTTPS, CORS y compresión**: fuera de v1; cuando llegue el frontend React, CORS se
  resolverá en un work item propio (el gateway es el lugar natural, pero la política de orígenes
  depende del despliegue del frontend).
- **Tracing distribuido** (OpenTelemetry/traceId propagado a logs de todos los servicios): v1 sólo
  garantiza `X-Correlation-Id` en el gateway y hacia el downstream.
- **Circuit breaker / reintentos hacia downstreams**: es el ítem del backlog
  `docs/FIX-0007-circuit-breaker.md`, contrato separado.
- **Métricas Prometheus/paneles**: no en v1 (sólo log estructurado de acceso).

> Notas de implementación (no spec, no generan AC): sin dependencias nuevas — `WebClient` para el
> proxy, `RouterFunction`/`WebFilter` para rutas y límites, `ReactorNettyWebSocketClient` +
> `WebSocketHandler` para el puente WS (las tres ya se usan en el proyecto). El token bucket y el
> matching de rutas son clases de dominio puras y testeables con reloj inyectado; el IT usa
> downstreams stub (`com.sun.net.httpserver.HttpServer` y un WS de Reactor Netty en proceso) para
> contar invocaciones sin Docker, más un IT de compose-docs para AC-001/AC-011.

## Ambiguity Log
- [x] Tecnología del punto de entrada: RESUELTO (humano 2026-09-11) = **gateway propio en
  WebFlux** dentro del stack (cero dependencias nuevas; control total del `429` + `Retry-After` +
  body de dominio; WS con las librerías ya usadas). Alternativas descartadas: Spring Cloud
  Gateway (el starter no está en el `.m2` y hay que resolver una release train compatible con
  Boot 4.1; igual requiere filtros propios) y Traefik (su middleware `rateLimit` genera el `429`
  sin `Retry-After` ni body configurable → incumple BR-04/BR-006 del contrato y rompe la
  convención `{"code","message"}`).
- [x] Tipo e ID: RESUELTO (humano 2026-09-11) = **FEAT-0007** (agrega un componente y capacidades
  nuevas; no es un bugfix), promocionado desde `docs/FIX-0005-gateway-rate-limiting.md`.
- [x] Topología de puertos: RESUELTO (humano 2026-09-11) = **cerrar todo detrás del gateway**;
  el debug directo queda en `docker-compose.dev.yml` documentado (BR-012).
- [x] Valores de rate limit: RESUELTO (humano 2026-09-11) = **moderados**: login 10/60 s (burst
  10), lectura 120/60 s (burst 60), default 300/60 s (burst 100), upgrade WS 30/60 s (burst 30),
  todos configurables.
- [x] Auth de WebSocket: RESUELTO (humano 2026-09-11) = **fuera de alcance**, documentado como
  brecha conocida (BR-011 y ADR-0016) y derivado a un work item propio.
- [x] Clave del rate limit ("por IP o por token", BR-03 del doc origen): RESUELTO (orquestador
  2026-09-11, confirmado en HO-Gate) = **por IP de origen**, con `confiar-forwarded-for: false`
  por default para no permitir evasión por header; el cupo por token requeriría que el gateway
  entienda el JWT (fuera de alcance) y se documenta como evolución.
- [x] Referencia rota del doc origen ("ver FIX-0002/FIX-0009"): RESUELTO (orquestador 2026-09-11)
  = **BR-008 pasa a tener AC propio** (`X-Correlation-Id` propagado/generado, reflejado y
  logueado); no se cita ningún FIX inexistente y el tracing distribuido queda fuera de alcance.
