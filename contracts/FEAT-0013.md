## Intent
Crear el microservicio `query-api` (services/query-api): capa de **lectura** del
pipeline. Expone el histórico de lecturas de un sensor (keyset, con selección de
fuente raw/agregados según el rango — spec §9.2), la última lectura y un canal
tiempo real por sensor (WS). Roles de lectura `{ADMIN, VIEWER}` (igual que los
endpoints de lectura de sensor-registry). Fuente spec: §3, §7
(`GET /api/sensores/{id}/lecturas`, `GET .../actual`, `WS /ws/sensores/{id}`),
§9.2 (raw < 7 días; agregados horario/diario para rangos largos), §9.4 (keyset),
stack.md.

## Use Case
**Actor:** Usuario autenticado `ADMIN` o `VIEWER`
**Goal:** Consultar lecturas históricas, la última lectura y recibir lecturas en
tiempo real de un sensor

### Main Flow
1. `GET /api/sensores/{id}/lecturas?desde&hasta&cursor&limit` (roles ADMIN/VIEWER):
   el sistema selecciona la fuente según el rango (§9.2; ver Ambiguity Log) y
   devuelve lecturas ordenadas DESC por `ts`, paginadas por **cursor keyset**
   (`(ts)` opaco), `limit` default 100 máx 1000 (regla §9.4).
2. `GET /api/sensores/{id}/actual`: devuelve la última lectura del sensor (fuente
   según Ambiguity Log).
3. `WS /ws/sensores/{id}`: suscripción push de lecturas en tiempo real del sensor
   (source según Ambiguity Log).

### Alternative Flows
- AF-01: Sin `Authorization` (o token inválido) → `401 UNAUTHENTICATED`.
- AF-02: Rol fuera de `{ADMIN, VIEWER}` → `403 INSUFFICIENT_ROLE`.
- AF-03: Sensor inexistente (sin lecturas y no validable) → `404 SENSOR_NOT_FOUND`
  en `/actual`; en histórico sin lecturas → `200 []` (rango sin datos no es error).
- AF-04: Parámetros inválidos (`limit` fuera de [1,1000], `desde>hasta`, cursor
  malformado, id no UUID) → `400` con codes (`SENSOR_INVALID_LIMIT`,
  `SENSOR_INVALID_CURSOR`, `SENSOR_INVALID_ID`, `INVALID_RANGE`).
- AF-05: Sin datos en el rango pedido → `200` lista vacía sin `nextCursor`.
- AF-06: WS sin auth o handshake inválido → se rechaza la conexión (close 1008).

## Business Rules
- BR-001: Consultas históricas paginadas **keyset/cursor**, nunca OFFSET; orden DESC
  por `ts`; `limit` default 100, máx 1000 (spec §9.4); cursor opaco (codifica ts de
  la última fila).
- BR-002: Rango temporal obligatorio en histórico (`desde`,`hasta` ISO-8601):
  `desde ≤ hasta`, ambos dentro de la ventana aceptada; ausencia o inversión →
  `400 INVALID_RANGE`. Sin `limit` → 100.
- BR-003: Fuente según rango (spec §9.2): rango < 7 días → tabla raw `lectura`;
  rango ≥ 7 días → agregados horario/diario **cuando existan** (v1: raw — ver
  Ambiguity Log). La elección es interna y transparente para el cliente.
- BR-004: `/actual` devuelve la última lectura del sensor (ts máximo); sin
  lecturas → `404 SENSOR_NOT_FOUND` (o code `LECTURAS_NOT_FOUND` según decisión).
- BR-005: WS `/ws/sensores/{id}` entrega solo lecturas de ese sensor en tiempo real;
  el payload es el mismo `{sensorId, timestamp, valor, unidadMedida}` del stream.
- BR-006: Roles de lectura `{ADMIN, VIEWER}` para REST y WS (validación JWT igual a
  sensor-registry; secreto compartido `AUTH_JWT_SECRET`).
- BR-007: Stack reactivo: WebFlux + R2DBC (lectura TimescaleDB) + consumer Reactor
  RabbitMQ (para WS si aplica); cero bloqueante; hexagonal.
- BR-008: No escribe datos: query-api solo lee (DB/Redis/stream); sin endpoint de
  escritura. Rechaza inputs inválidos con codes estables (nunca 500).

## Acceptance Criteria
- AC-001: GIVEN un sensor con N>limit lecturas en TimescaleDB y un request
  `GET /api/sensores/{id}/lecturas?desde&hasta` con JWT ADMIN sin cursor
  WHEN el sistema responde
  THEN `200` con `limit` lecturas DESC por ts y `nextCursor` presente (hay más).
- AC-002: GIVEN el `nextCursor` de AC-001
  WHEN se pide la página siguiente con el mismo rango
  THEN devuelve las siguientes lecturas sin duplicados ni saltos (empates de ts
  resueltos por `(ts, id)` de fila — keyset compuesto si aplica).
- AC-003: GIVEN un sensor sin lecturas en el rango
  WHEN `GET .../lecturas?desde&hasta`
  THEN `200` con `[]` y sin `nextCursor`.
- AC-004: GIVEN `limit=1001` o `limit=0` o `desde>hasta` o id malformado
  WHEN el sistema procesa el request
  THEN `400` con el code correspondiente (`SENSOR_INVALID_LIMIT`, `INVALID_RANGE`,
  `SENSOR_INVALID_ID`).
- AC-005: GIVEN un sensor con al menos una lectura
  WHEN `GET /api/sensores/{id}/actual` con JWT VIEWER
  THEN `200` con la lectura de ts máximo (payload Lectura).
- AC-006: GIVEN un sensor sin lecturas
  WHEN `GET /api/sensores/{id}/actual`
  THEN `404` (code según decisión).
- AC-007: GIVEN un cliente suscripto a `WS /ws/sensores/{id}` y lecturas nuevas de
  ese sensor publicadas en `sensor.lecturas`
  WHEN el sistema procesa las lecturas
  THEN el cliente recibe cada lectura (o las recientes) de ese sensor por el WS
  (verificado en IT con Rabbit real y cliente WS).
- AC-008: GIVEN request sin `Authorization` o con rol `VIEWER` válido
  WHEN `GET .../lecturas`
  THEN `401 UNAUTHENTICATED` (sin token) y `200` con VIEWER (lectura permitida).

## Entities Affected
- Lectura (persistida por ingestion en TimescaleDB hypertable `lectura`): **lectura
  histórica** y última lectura. query-api no persiste nada (BR-008).
- Sensor (config en sensor-registry): no se modifica; el WS/endpoints usan su id.
- Stream `sensor.lecturas`: reutilizado como fuente de tiempo real si aplica.

> Notas de implementación (no spec, no generan AC): módulo Maven nuevo standalone;
> `domain` (Lectura consultable, cursor opaco), `application` (port de consulta:
> `LecturasHistoricasPort`, `UltimaLecturaPort`, puerto de suscripción para WS),
> `infrastructure`: adapter R2DBC sobre `lectura`, consumer de `sensor.lecturas`
> para el bus tiempo real (cola propia de query-api), WebSocket
> `/ws/sensores/{id}`, y verificación JWT (HS256 con `AUTH_JWT_SECRET`, mismo
> formato que FEAT-0006 — util propio en este módulo, sin compartir artefacto por
> ahora, poms standalone).

## Ambiguity Log
- [x] Fuente de datos: RESUELTO (humano 2026-09-09) = **lectura directa (solo-lectura) de la TimescaleDB** de ingestion
      misma TimescaleDB donde ingestion persiste** (query-api es la capa de
      consulta del timeseries; stack "no acceder a DB de otro servicio" se
      interpreta como no escribir/leer metadata ajena — acá se lee el modelo de
      datos que este servicio expone). Alternativa estricta = pasar por API/eventos
      (inviable para rangos históricos). Requiere decisión humana.
- [x] `/actual`: RESUELTO (humano 2026-09-09) = **último row de la DB** (sin Redis en v1) (correcto, sin Redis en
      v1; Redis queda como optimización multi-instancia/alta concurrencia).
      Alternativa = ingestion escribe Redis por lectura (reabre FEAT-0011) y acá se
      lee Redis. Requiere decisión humana.
- [x] Agregados §9.2: RESUELTO (humano 2026-09-09) = **v1 raw para cualquier rango**; regla raw<7d/agregados al existir en infra
      (volumen dev pequeño; source-selection raw<7d / agregados se activa cuando
      existan agregados materializados en la fase de infra). Alternativa = crear ya
      continuous aggregates y políticas (más TimescaleDB en este Work Item).
      Requiere decisión humana.
- [x] Tiempo real WS: RESUELTO (humano 2026-09-09) = query-api **consume `sensor.lecturas`** (cola propia) y hace broadcast por sensor con cola
      propia y hace broadcast por sensor (idempotente multi-consumidor, sin tocar
      ingestion). Alternativa = no consumir y solo re-publicar el bus de
      `sensor.alertas`. Requiere decisión humana.
