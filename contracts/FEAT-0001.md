## Acceptance Criteria
- AC-001: GIVEN no existe sensor con `codigo` = `PARANA-RECONQUISTA` en el sistema, y un
  request `POST /api/sensores` con header `Authorization` con JWT rol `ADMIN` y cuerpo válido
  (`codigo` = `PARANA-RECONQUISTA`, `nombre` = `Reconquista`, `tipo` = `RIO`, `latitud` = `-29.15`,
  `longitud` = `-59.65`, `unidadMedida` = `METROS`, `rangoNormal` = {min:4, max:6},
  `rangoWarning` = {min:2, max:8}, `rangoCritical` = {min:0, max:10}, `histeresis` = `0.5`,
  `frecuenciaReporteSegundos` = `60`, `estado` = `ACTIVO`)
  WHEN el sistema procesa el request
  THEN responde `201 Created` con body conteniendo un `id` UUID no nulo, `codigo` = `PARANA-RECONQUISTA`,
  `nombre` = `Reconquista`, y los tres rangos persistidos (`rangoNormal`, `rangoWarning`,
  `rangoCritical`), y se publica un evento de creación de sensor a RabbitMQ
- AC-002: GIVEN existe un sensor con `codigo` = `PARANA-RECONQUISTA`, y un request
  `POST /api/sensores` con header `Authorization` con JWT rol `ADMIN` y cuerpo con
  `codigo` = `PARANA-RECONQUISTA` (resto de campos válidos)
  WHEN el sistema procesa el request
  THEN responde `409 CONFLICT` con body conteniendo código `SENSOR_CODE_DUPLICATED`
- AC-003: GIVEN un request `POST /api/sensores` con header `Authorization` con JWT rol `ADMIN`
  y rangos que violan BR-002 (`rangoCritical` = {min:5, max:9}, `rangoWarning` = {min:2, max:6},
  `rangoNormal` = {min:3, max:5}, de modo que `rangoCritical.min` (5) > `rangoWarning.min` (2))
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con body conteniendo código `SENSOR_INVALID_RANGES`
- AC-004: GIVEN un request `POST /api/sensores` con header `Authorization` con JWT rol `ADMIN`
  y `latitud` = `95` (resto de campos válidos, satisfaciendo BR-002, BR-005..BR-009)
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con body conteniendo código `SENSOR_INVALID_COORDINATES`
- AC-005: GIVEN un request `POST /api/sensores` con header `Authorization` con JWT rol `ADMIN`

  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con body conteniendo código `SENSOR_INVALID_COORDINATES`
- AC-006: GIVEN el request `POST /api/sensores` incluye header `Authorization` con JWT rol

  WHEN el sistema procesa el request

- AC-007: GIVEN el request `POST /api/sensores` no incluye header `Authorization` y cuerpo válido
  WHEN el sistema procesa el request
  THEN responde `401 UNAUTHORIZED`
- AC-008: GIVEN un request `POST /api/sensores` con header `Authorization` con JWT rol `ADMIN`
  y `histeresis` = `-0.5` (resto de campos válidos, satisfaciendo BR-002, BR-003, BR-004, BR-006..BR-009)
  WHEN el sistema procesa el request

## Entities Affected
- Sensor (owner=sensor-registry): atributos `codigo`, `nombre`, `tipo`, `latitud`, `longitude`,
  `unidadMedida`, `estado`, `histeresis`, `frecuenciaReporteSegundos`, `fechaInstalacion`,
  y los tres rangos
  `rangoNormal`, `rangoWarning`, `rangoCritical` (cada uno un `Rango {min: decimal, max: decimal}`) |
  invariantes aplicables: BR-001 (unicidad de `codigo`), BR-002 (anidamiento inclusivo
  de los tres rangos — el invariante central de la entidad), BR-003 (`latitud` ∈ [-90, 90]),
  BR-004 (`longitud` ∈ [-180, 180]), BR-005 (`histeresis` ≥ 0), BR-006
  (`frecuenciaReporteSegundos` > 0), BR-007 (`estado` ∈ {ACTIVO, INACTIVO, MANTENIMIENTO}),
  BR-008 (`unidadMedida` ∈ {METROS, CENTIMETROS}), BR-009 (`tipo` ∈ {RIO, ARROYO, BAÑADO}).
  Additionally, `fechaInstalacion` is set by the system on creation (timestamp).
- Rango (value object del dominio de Sensor): `{ min: decimal, max: decimal }` |
  invariante: BR-002 vincula tres instancias (rangoNormal ⊆ rangoWarning ⊆ rangoCritical)
  mediante anidamiento inclusivo —
  `rangoCritical.min ≤ rangoWarning.min ≤ rangoNormal.min ≤ rangoNormal.max ≤ rangoWarning.max ≤ rangoCritical.max`.
- Usuario (owner=sensor-registry): atributos `id`, `email`, `rol` | sin invariantes de
  los BR-001..BR-009 del presente Contract. El actor del Use Case es `Usuario` con `rol=ADMIN`;
  el control de acceso/rol se expresa vía AF-04 / AC-006 como regla de comportamiento, no como
  invariante de entidad. Invariantes fuera de alcance (p. ej. `passwordHash`, formato de
  `email`, unicidad de `email`) pertenecen a un futuro Contract de auth y no se listan aquí.
- Lectura (referenced FK, owner=ingestion-service): `sensorId` referencia a `Sensor.id` |
  `sensor-registry` nunca ejecuta DELETE físico de un Sensor mientras existan filas de
  `Lectura` que lo referencien; la baja es lógica (cambio de `estado` a `INACTIVO`,
  segundo ítem resuelto del Ambiguity Log).

## Ambiguity Log
- [x] Auth: `sensor-registry` emite y valida JWT (rol `ADMIN` / `VIEWER`).
- [x] Borrado: baja lógica (cambio de estado a `INACTIVO`). Nunca DELETE físico
      mientras existan lecturas referenciando al sensor.
- [x] Histéresis: se acepta `histeresis >= 0`. Cero desactiva el margen (severidad
      cambia inmediato también al bajar).
- [x] Edición de rangos/histéresis: aplica sólo a lecturas futuras. Sin reproceso
      retroactivo de severidad ya emitida.
- [x] Evento de creación de sensor: el spec no define exchange/routing key ni
      payload del evento "sensor creado" (solo define `sensor.lecturas` y
      `sensor.alertas`). AC-001 verifica publicación a RabbitMQ pero no puede
      asertar exchange ni routing key específicos. → RESUELTO v1 (decisión
      humana 2026-07-25): exchange `sensor.created` (topic, durable), routing
      key `sensor.created.{id}`, payload mínimo `{ "sensorId": "<uuid>",
      "codigo": "<codigo>" }`. Formalizado como contrato v1; enriquecer el
      payload en Gate futuro cuando exista consumer que lo requiera (YAGNI: no
      hay consumer de este evento en el presente Contract).
- [x] [Main Flow step 1] vs [AC-001]: El Main Flow lista explícitamente `nombre` entre los
      datos enviados por el cliente, y el cuerpo "válido" de AC-001 lo incluye
      (`nombre` = `Reconquista`), y Entities Affected lo lista. → RESUELTO (decisión
      humana 2026-07-25): opción (a) — `nombre` es **requerido**; presente en AC-001
      body y Entities Affected. Implementado como `@NotBlank` en `SensorRequest` y
      `Objects.requireNonNull` en `Sensor`. AC-001 (que lo envía) espera `201`:
      consistente.
- [x] [AC-001]: `fechaInstalacion` es atributo de Sensor según base spec §4; Entities
      Affected declara "set by the system on creation (timestamp)" y el cuerpo de
      AC-001 no lo envía. → RESUELTO (decisión humana 2026-07-25): opción (a) —
      **system-set** (= `Instant.now()` al crear, no cliente-provee).
      Implementado en `CreateSensorService` (`Instant.now()`); no figura en
      `SensorRequest`. AC-001 (que lo omite) espera `201`: consistente.
- [x] [AC-003] vs [BR-002]: La GIVEN de AC-003 cita la violación correcta
      (`rangoCritical.min` (5) > `rangoWarning.min` (2)), que SÍ rompe la cadena de
      anidamiento de BR-002. → RESUELTO (decisión humana 2026-07-25): opción (a) —
      racional corregida en AC-001 (la fuente de verdad es la cadena BR-002, no la
      racional vieja `rangoCritical.min < rangoWarning.max`). Implementado en
      `CreateSensorService.validateRanges` valida la cadena completa
      `critical.min ≤ warning.min ≤ normal.min ≤ normal.max ≤ warning.max ≤ critical.max`.
      AC-001 (`critical.min`=0 < `warning.max`=8) pasa; AC-003 (datos violadores) →
      `400 SENSOR_INVALID_RANGES`. Sin riesgo de falsos rechazos.
