> **Fase B** del frontend: convertir el dashboard de sólo lectura en una herramienta de operación.

## Intent
El SPA muestra el estado del sistema pero no permite operarlo: dar de alta un sensor, corregir sus
bandas o darlo de baja sigue siendo trabajo de `curl`, y la demo necesita arrancar el generador de
lecturas sin salir de la aplicación. Este work item agrega las pantallas de **administración**
(alta, edición y baja lógica de sensores, con validación en cliente y los errores de dominio del
backend mostrados por `code`) y el **panel de demo** que controla el simulador cuando está habilitado
por configuración (el simulador **no** tiene ruta en el gateway, por decisión de `FEAT-0008`).

## Use Case
**Actor:** usuario `ADMIN` (escritura) y `VIEWER` (sólo lectura: nunca ve las acciones de escritura).
**Goal:** administrar el catálogo de sensores y operar la demo desde la misma interfaz, sin `curl` y
sin adivinar por qué falló una operación.

### Main Flow
1. `ADMIN` entra a **Sensores** y ve el listado paginado (`GET /api/sensores`, keyset) con código,
   nombre, tipo, estado y unidad, más el buscador/orden disponible.
2. Elige **Nuevo sensor**, completa el formulario (código, nombre, tipo, ubicación, unidad, rangos
   normal/warning/critical, histéresis, frecuencia de reporte) con validación en cliente y envía
   `POST /api/sensores`.
3. El backend responde `201`: el SPA informa el alta, refresca el listado y el sensor aparece en el
   mapa (`FEAT-0009`) con su estado real.
4. Desde un sensor existente, `ADMIN` edita su configuración (`PUT /api/sensores/{id}`, subset completo
   de configuración) o lo da de baja con confirmación explícita (`DELETE`, baja lógica → `INACTIVO`).
5. En el **panel de demo** (visible sólo si está configurado y con el override de dev levantado),
   `ADMIN` arranca/detiene el simulador y ve el estado y las lecturas publicadas.
6. Todas las operaciones terminan con un resultado visible (éxito o error del dominio) y el listado
   queda consistente con lo que devolvió el backend.

### Alternative Flows
- AF-01: `409 SENSOR_CODE_DUPLICATED` → el error se marca **en el campo `codigo`** con el mensaje del
  `code`, sin perder lo cargado en el resto del formulario.
- AF-02: `400 SENSOR_INVALID_*` (rango invertido, histéresis negativa, frecuencia inválida, body
  incompleto) → cada violación se muestra junto al campo correspondiente; si el backend manda un
  `code` inesperado, se muestra tal cual en el resumen del formulario.
- AF-03: `404 SENSOR_NOT_FOUND` al editar o dar de baja algo que otro usuario ya borró → mensaje
  claro, el formulario se cierra y el listado se refresca (no se reintenta a ciegas).
- AF-04: sensor `INACTIVO` → se muestra como tal y **no** se ofrece editarlo (el backend lo rechaza);
  sí se explica cómo reactivarlo (editando su estado) si el contrato lo permite.
- AF-05: usuario `VIEWER` → el listado es de sólo lectura: no hay botones de alta/edición/baja ni
  panel de demo (no se ofrecen acciones que el backend va a rechazar).
- AF-06: el panel de demo está deshabilitado (sin `VITE_SIMULADOR_URL`) o el simulador no está
  levantado → el panel no aparece o muestra cómo habilitarlo (`docker-compose.dev.yml`), sin errores
  de red crudos; `409 SIMULATOR_ALREADY_RUNNING` / `SIMULATOR_NOT_RUNNING` se informan por `code`.
- AF-07: `429` al escribir → se espera el `Retry-After`, se mantiene el formulario con los datos y no
  se reenvía automáticamente (una escritura no se reintenta sola: podría duplicar).
- AF-08: el token vence en medio de una edición → se re-loguea y, tras el login, se recupera el
  formulario con lo cargado (o se avisa antes de perderlo), sin enviar la operación dos veces.

## Business Rules
- BR-001: **La autorización se refleja en la UI, pero la decide el backend**: las acciones de
  escritura sólo se muestran a `ADMIN`; si el backend responde `401`/`403`, el SPA lo informa por
  `code` y no reintenta. La UI nunca es la única barrera (el guard de rol no reemplaza al backend).
- BR-002: **Los errores de dominio se muestran por `code`** (mismo diccionario de `FEAT-0009` BR-004),
  mapeados al campo cuando el `code` lo permite (`SENSOR_CODE_DUPLICATED` → `codigo`,
  `SENSOR_INVALID_*` → el campo correspondiente); el status y el `X-Correlation-Id` quedan en el
  detalle técnico. Nunca se muestra un error genérico "algo salió mal" si el backend dio un `code`.
- BR-003: El formulario valida en cliente **lo mismo** que el backend (rangos coherentes
  `normal ⊂ warning ⊂ critical`, histéresis ≥ 0, frecuencia ≥ 1, unidad/tipo de la lista soportada) y
  la validación de cliente **nunca** reemplaza la del servidor; el envío queda bloqueado mientras hay
  errores locales.
- BR-004: `PUT` envía el **subset de configuración completo** (no parches parciales) y el SPA no
  inventa campos fuera del DTO (`FEAT-0004` rechaza campos desconocidos con
  `SENSOR_INVALID_REQUEST`): un campo nuevo obliga a tocar el contrato, no el formulario.
- BR-005: La **baja es lógica y con confirmación explícita** (el sensor pasa a `INACTIVO`, no se borra
  físicamente): la UI lo dice con esas palabras, no promete eliminación, y tras la baja el listado y
  el mapa muestran el estado real.
- BR-006: **Ninguna escritura se reintenta automáticamente** (a diferencia de las lecturas): ante
  error de red o `5xx` se informa y el usuario decide; ante `429` se espera el `Retry-After`. Esto
  evita altas o bajas duplicadas.
- BR-007: El **panel del simulador está apagado por default**: sólo se muestra si
  `VITE_SIMULADOR_URL` está configurada (el simulador está **fuera del gateway** por `FEAT-0008`
  BR-010, así que en producción no hay ruta y el panel queda oculto por configuración, no por código
  condicional hardcodeado). El panel es de demo: se documenta que requiere `docker-compose.dev.yml`.
- BR-008: El listado administrativo usa **paginación keyset** del backend (nunca OFFSET ni "traer
  todo"), respeta el cupo del gateway y no hace N+1 para mostrar el estado de cada sensor.
- BR-009: Accesibilidad y UX: formularios con `label` asociado, errores anunciados por `aria-live` y
  foco en el primer campo inválido; acciones destructivas requieren confirmación; nunca se pierde lo
  cargado por un error del servidor.
- BR-010: Todo configurable y documentado: `VITE_SIMULADOR_URL`, tamaño de página del listado y
  timeouts de escritura en variables `VITE_*` con default documentado (`RUNBOOK.md`), incluido cómo
  habilitar el panel y el simulador para la demo (`docker-compose.dev.yml`); `ARQUITECTURA.md`
  documenta por qué el simulador no pasa por el gateway. Ningún valor hardcodeado.

## Acceptance Criteria
- AC-001 (Main Flow 1): GIVEN un `ADMIN` WHEN entra a Sensores THEN ve el listado keyset con estado y
  unidad, y puede avanzar de página sin duplicados ni saltos.
- AC-002 (Main Flow 2/3): GIVEN un formulario válido WHEN se envía THEN se crea el sensor (`201`), el
  listado se refresca y el sensor aparece en el mapa con su estado.
- AC-003 (AF-01, BR-002): GIVEN un `codigo` ya existente WHEN se envía el alta THEN el error se marca
  en el campo `codigo` con el mensaje del `409 SENSOR_CODE_DUPLICATED` y el resto del formulario queda
  intacto.
- AC-004 (AF-02, BR-003): GIVEN rangos invertidos o histéresis negativa WHEN se completa el formulario
  THEN el envío está bloqueado con el error local en el campo, y GIVEN que el backend los rechaza
  THEN el mensaje del `code` se muestra junto al campo correspondiente.
- AC-005 (Main Flow 4, BR-005): GIVEN un sensor existente WHEN `ADMIN` lo edita THEN el `PUT` envía el
  subset completo y el listado/mapa reflejan la configuración nueva; GIVEN una baja WHEN se confirma
  THEN el sensor queda `INACTIVO` (visible en listado y mapa) y la UI no dice que se eliminó.
- AC-006 (AF-03): GIVEN que el sensor fue borrado por otro usuario WHEN se intenta editar THEN se
  muestra `404 SENSOR_NOT_FOUND`, el formulario se cierra y el listado se refresca.
- AC-007 (AF-05, BR-001): GIVEN un usuario `VIEWER` WHEN navega el módulo THEN no hay botones de
  escritura ni panel de demo, y GIVEN que fuerza una petición de escritura THEN el `403` se informa por
  `code` sin romper la sesión.
- AC-008 (AF-07, BR-006): GIVEN una escritura WHEN el gateway responde `429` con `Retry-After` THEN el
  SPA avisa, mantiene los datos cargados y **no** reenvía la operación automáticamente.
- AC-009 (BR-007, AF-06): GIVEN el SPA sin `VITE_SIMULADOR_URL` WHEN se navega THEN el panel de demo
  no aparece; GIVEN que está configurada y el simulador responde `409`/`409 NOT_RUNNING` THEN el
  mensaje sale del `code` y no de un error de red crudo.
- AC-010 (AF-04): GIVEN un sensor `INACTIVO` WHEN se abre su fila THEN se muestra su estado y no se
  ofrece editarlo, con la explicación de cómo reactivarlo.
- AC-011 (AF-08): GIVEN una edición en curso WHEN el token vence THEN el SPA re-loguea y no envía la
  operación dos veces (ni pierde silenciosamente lo cargado: avisa y conserva el formulario).
- AC-012 (BR-010): GIVEN documentos y código WHEN se revisan THEN `VITE_SIMULADOR_URL`, el tamaño de
  página y los timeouts están documentados en el RUNBOOK, el motivo por el que el simulador no pasa
  por el gateway está en ARQUITECTURA y no hay valores hardcodeados en los componentes.

## Entities Affected
- **SPA (`web/`)**: rutas de administración (`/sensores/nuevo`, `/sensores/{id}/editar`), listado
  keyset, formulario con validación y mapeo `code → campo`, confirmación de baja, panel de demo
  configurable, integración con el mapa y el listado de `FEAT-0009`.
- **Backend**: **sin cambios**. Se consumen `GET/POST/PUT/DELETE /api/sensores` (`FEAT-0001`..0005) y
  el control del simulador (`FEAT-0010`) **sólo** por el puerto de desarrollo (`docker-compose.dev.yml`),
  sin agregar ruta al gateway (`FEAT-0008` BR-010).
- **Docs**: `RUNBOOK.md` (cómo habilitar el panel de demo y probar el CRUD desde el SPA),
  `ARQUITECTURA.md` (rol del simulador fuera del gateway), `README.md`, `REGISTRO-SDD.md`,
  `ESTADO-SDD.md`, `ESTADO-PROYECTO.md`, `CHANGELOG.md`.
- **Datos**: el SPA **escribe** por primera vez (alta/edición/baja lógica) — siempre a través de la API
  existente, sin lógica de negocio duplicada en el cliente.
