## Intent
Exponer `GET /api/sensores/{id}` en `sensor-registry` para obtener el detalle
completo de un sensor registrado por su `id` (UUID). Reutiliza el shape de
`SensorResponse` de FEAT-0001/FEAT-0002, el guard de lectura `{ADMIN, VIEWER}`
(`RolGuard.requireReader`, FEAT-0002) y el stack reactivo (WebFlux/R2DBC).
Fuente spec: §7 (`GET /api/sensores` — detalle por id), §4 Sensor.

## Use Case
**Actor:** Usuario autenticado con rol `ADMIN` o `VIEWER`
**Goal:** Obtener el detalle completo de un sensor por su `id`

### Main Flow
1. El actor envía `GET /api/sensores/{id}` con header `Authorization`
   (JWT rol `ADMIN` o `VIEWER`).
2. El sistema valida el token y el rol (vía `RolGuard.requireReader`), valida que
   `{id}` sea un UUID bien formado (400 si no lo es) y consulta el sensor por id.
3. Si el sensor existe → responde `200 OK` con el `SensorResponse` completo
   (mismos campos que el POST de FEAT-0001 / ítem del listado de FEAT-0002).
   Si no existe → responde `404 SENSOR_NOT_FOUND`.

### Alternative Flows
- AF-01: Sin header `Authorization` (o token inválido) → `401 UNAUTHENTICATED`.
- AF-02: Rol del token fuera de `{ADMIN, VIEWER}` (sentinel `OTHER`) →
  `403 INSUFFICIENT_ROLE`.
- AF-03: `{id}` es un UUID válido pero no existe sensor con ese id →
  `404 SENSOR_NOT_FOUND`.
- AF-04: `{id}` no es parseable como UUID (malformado) →
  `400 SENSOR_INVALID_ID` (ver Ambiguity Log).
- AF-05: El sensor existe pero está en estado `INACTIVO`/`MANTENIMIENTO` →
  `200 OK` igual (el detalle no filtra por estado — ver Ambiguity Log).

## Business Rules
- BR-001: El path param `{id}` debe ser un UUID válido. Id malformado →
  `400 SENSOR_INVALID_ID` (nunca 500).
- BR-002: Para un id UUID válido, si no existe sensor con ese id → `404 SENSOR_NOT_FOUND`
  con body `{"code","message"}` (nunca 500, nunca `200` con body vacío).
- BR-003: La lectura del detalle está permitida a `{ADMIN, VIEWER}`. Rol fuera del
  par → `403 INSUFFICIENT_ROLE`. (Precedente FEAT-0002 BR-006; la spec §7 que rotula
  GET como "(admin)" quedó superada por esa decisión humana.)
- BR-004: Sin `Authorization` (o token no reconocido → rol `null`) → `401 UNAUTHENTICATED`.
  (Precedente FEAT-0002 BR-007.)
- BR-005: El body del detalle es el estado completo persistido del sensor: mismos
  campos y tipos que `SensorResponse` de FEAT-0001/FEAT-0002 (`id`, `codigo`, `nombre`,
  `tipo`, `latitud`, `longitud`, `unidadMedida`, `estado`, `histeresis`,
  `frecuenciaReporteSegundos`, `fechaInstalacion`, `rangoNormal`, `rangoWarning`,
  `rangoCritical`). Sin campos derivados.
- BR-006: El detalle no filtra por estado: sensores `INACTIVO`/`MANTENIMIENTO` se
  devuelven con su estado real (consistente con el listado FEAT-0002). La visibilidad
  post-baja la definirá FEAT-0005 (borrado lógico), no este Contract.

## Acceptance Criteria
- AC-001: GIVEN existe un sensor con `id` = `X` (estado `ACTIVO`, datos completos:
  `codigo` = `PARANA-RECONQUISTA`, `tipo` = `RIO`, rangos normal/warning/critical
  persistidos, `histeresis` = `0.5`) y un request `GET /api/sensores/{X}` con header
  `Authorization` con JWT rol `ADMIN`
  WHEN el sistema procesa el request
  THEN responde `200 OK` con body conteniendo `id` = `X` y el resto de los campos
  idénticos al sensor persistido (mismo shape que FEAT-0001/FEAT-0002).
- AC-002: GIVEN el mismo sensor y un request `GET /api/sensores/{X}` con JWT rol `VIEWER`
  WHEN el sistema procesa el request
  THEN responde `200 OK` con la misma estructura que AC-001 (VIEWER puede leer el detalle).
- AC-003: GIVEN un request `GET /api/sensores/{X}` sin header `Authorization`
  WHEN el sistema procesa el request
  THEN responde `401 UNAUTHORIZED` con body conteniendo código `UNAUTHENTICATED`.
- AC-004: GIVEN un request `GET /api/sensores/{X}` con JWT cuyo rol no pertenece a
  `{ADMIN, VIEWER}` (ej. sentinel `OTHER`)
  WHEN el sistema procesa el request
  THEN responde `403 FORBIDDEN` con body conteniendo código `INSUFFICIENT_ROLE`.
- AC-005: GIVEN no existe sensor con `id` = `Y` (UUID válido no registrado) y un request
  `GET /api/sensores/{Y}` con JWT rol `ADMIN`
  WHEN el sistema procesa el request
  THEN responde `404 NOT FOUND` con body conteniendo código `SENSOR_NOT_FOUND`.
- AC-006: GIVEN un request `GET /api/sensores/no-es-un-uuid` con JWT rol `ADMIN`
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con body conteniendo código `SENSOR_INVALID_ID`.
- AC-007: GIVEN existe un sensor con `id` = `Z` en estado `INACTIVO` y un request
  `GET /api/sensores/{Z}` con JWT rol `ADMIN`
  WHEN el sistema procesa el request
  THEN responde `200 OK` con body conteniendo `estado` = `INACTIVO` (sin filtrar).

## Entities Affected

  rangos). Sin invariantes nuevos — reutiliza BR-001..BR-009 de `FEAT-0001`

> Nota de impl (no es spec, no genera AC): requiere un port out de lectura por id

## Ambiguity Log

      (decisión humana 2026-08-13/14, BR-006) ya resolvió lectura `{ADMIN, VIEWER}` para
      el listado. → RESUELTO por precedente: mismo par para el detalle (BR-003). Si se
      quisiera detalle ADMIN-only, es un cambio de spec — avisar antes de aprobar.
- [x] Code HTTP para `{id}` malformado: RESUELTO (humano 2026-09-09) = **nuevo code
      `SENSOR_INVALID_ID` (400)**, consistente con la familia `SENSOR_INVALID_LIMIT/CURSOR`
      de FEAT-0002. Alternativa: reutilizar el code genérico `SENSOR_INVALID_REQUEST`
      (ya mapeado en `GlobalErrorHandler` para `TypeMismatchException`). Decisión: **SENSOR_INVALID_ID (400)**.
- [x] Visibilidad de sensores `INACTIVO`/`MANTENIMIENTO` en el detalle: RESUELTO (humano 2026-09-09) =
      devolver `200` sin filtrar (consistente con FEAT-0002, que lista todo estado).
      FEAT-0005 (borrado lógico) decidirá si la baja oculta el sensor de lecturas
      posteriores. Decisión: **devolver 200 sin filtrar por estado**.\n
