## Intent
Agregar autenticación real a `sensor-registry`: entidad `Usuario`
(`id,email,passwordHash,rol`), endpoint `POST /api/auth/login` que valida
credenciales y emite un **JWT firmado** (claims: `sub` = id de usuario, `rol` =
`ADMIN`/`VIEWER`, `exp`), y verificación de ese JWT en el `RolFilter` para todos
los endpoints protegidos (reemplaza el header literal `Bearer ROLE` de v1-fake).
Fuente spec: §4 Usuario, §7 (`POST /api/auth/login` → JWT), §9.1 (auth dentro de
`sensor-registry` en v1). Sin OAuth externo, sin refresh token ni blacklist en v1.

## Use Case
**Actor:** Usuario registrado del sistema (rol `ADMIN` o `VIEWER`)
**Goal:** Obtener un JWT válido presentando email + password, y usarlo para acceder
a los endpoints protegidos (`POST/GET /api/sensores…`)

### Main Flow
1. El actor envía `POST /api/auth/login` con body `{"email": "...", "password": "..."}`.
2. El sistema valida el body (email formato y password no vacía → 400 si no),
   busca el `Usuario` por email y verifica el hash de la password (BCrypt).
3. Si las credenciales son válidas → `200 OK` con `{"token": "<jwt>", "rol":
   "ADMIN|VIEWER", "expiraEnSegundos": N}`; el JWT queda firmado con el secreto
   configurado. Si no → `401 INVALID_CREDENTIALS`.
4. En requests posteriores, `RolFilter` verifica firma y expiración del
   `Authorization: Bearer <jwt>` y propaga el rol al Context (mismos guards
   `requireAdmin`/`requireReader` de FEAT-0001..0003).

### Alternative Flows
- AF-01: Body ausente o campos faltantes (`email`/`password`) → `400 SENSOR_INVALID_REQUEST`.
- AF-02: `email` con formato inválido → `400 SENSOR_INVALID_REQUEST`.
- AF-03: Email inexistente o password incorrecta → `401 INVALID_CREDENTIALS`
  (respuesta idéntica para ambos casos — no enumerar cuentas).
- AF-04: Header `Authorization: Bearer <token>` con JWT malformado, expirado o de
  firma inválida en un endpoint protegido → `401 UNAUTHENTICATED`.
- AF-05: Token legacy literal (`Bearer ADMIN` sin firma JWT) en un endpoint
  protegido → `401 UNAUTHENTICATED` (deja de ser aceptado — ver Ambiguity Log).
- AF-06: Secreto JWT: `application.yml` define un default **dev** documentado como
  no-seguro (`auth.jwt.secret`), sobreescribible vía env `AUTH_JWT_SECRET`; en
  entornos reales se exige setear el env (config, no código).

## Business Rules
- BR-001: La password nunca se almacena ni se devuelve en claro: `Usuario.passwordHash`
  es siempre un hash **BCrypt** (spring-security-crypto ya disponible en el stack).
- BR-002: `email` es único en `usuario` y se normaliza a minúsculas. Login distingue
  solo "credenciales inválidas" (401 `INVALID_CREDENTIALS`) — misma respuesta para
  email inexistente y password incorrecta.
- BR-003: El JWT emitido usa HS256 con claims `sub` (UUID del usuario), `rol`
  (`ADMIN`/`VIEWER`), `iat` y `exp = iat + auth.jwt.expiration-seconds`
  (default 3600 s, configurables). Firmado con `auth.jwt.secret`
  (override env `AUTH_JWT_SECRET`; default dev documentado como no-seguro, AF-06).
- BR-004: `RolFilter` verifica en cada request: presencia de header, firma HS256 y
  `exp` del token. Válido → rol del claim al Context; token ausente → sin rol
  (401 vía guard); token presente pero inválido/expirado → `UNAUTHENTICATED`;
  token válido con claim de rol ajeno a `{ADMIN,VIEWER}` → sentinel `OTHER` (403).
- BR-005: Stateless: sin refresh token, sin blacklist ni logout server-side en v1
  (expiración corta y secret rotable). El `rol` de un token es inmutable hasta su `exp`.
- BR-006: Los endpoints protegidos existentes (POST/GET de FEAT-0001..0003) exigen
  JWT real; no queda ningún camino de "rol literal" en producción (ver Ambiguity Log).

## Acceptance Criteria
- AC-001: GIVEN existe `usuario` con email `admin@wrsensor.local`, rol `ADMIN` y su
  hash BCrypt, y un request `POST /api/auth/login` con `{"email":"admin@wrsensor.local",
  "password":"<password-correcta>"}`
  WHEN el sistema procesa el request
  THEN responde `200 OK` con body `{token, rol=ADMIN, expiraEnSegundos>0}` y el token
  decodificado contiene `rol=ADMIN` y `exp` > now.
- AC-002: GIVEN un `usuario` VIEWER (`viewer@wrsensor.local`) y credenciales correctas
  WHEN `POST /api/auth/login`
  THEN responde `200 OK` con `rol=VIEWER`.
- AC-003: GIVEN un `usuario` existente y un request con `password` incorrecta
  WHEN `POST /api/auth/login`
  THEN responde `401 UNAUTHORIZED` con code `INVALID_CREDENTIALS`.
- AC-004: GIVEN un email inexistente y cualquier password
  WHEN `POST /api/auth/login`
  THEN responde `401 UNAUTHORIZED` con code `INVALID_CREDENTIALS` (idéntico a AC-003).
- AC-005: GIVEN un request `POST /api/auth/login` con `email` malformado o
  `password` vacía/faltante
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con code `SENSOR_INVALID_REQUEST`.
- AC-006: GIVEN un JWT válido emitido por login de un usuario `ADMIN`
  WHEN `GET /api/sensores/{id}` (endpoint protegido de FEAT-0003) con
  `Authorization: Bearer <jwt>`
  THEN responde `200 OK` (el guard `requireReader` acepta el rol del claim).
- AC-007: GIVEN un JWT con firma inválida o `exp` pasado
  WHEN un endpoint protegido recibe `Authorization: Bearer <jwt-invalido>`
  THEN responde `401 UNAUTHORIZED` con code `UNAUTHENTICATED`.
- AC-008: GIVEN un request a un endpoint protegido con el header legacy
  `Authorization: Bearer ADMIN` (rol literal, sin JWT)
  WHEN el sistema procesa el request
  THEN responde `401 UNAUTHORIZED` (el rol literal dejó de ser aceptado).

## Entities Affected
- Usuario (NUEVA, owner=sensor-registry): `id` UUID, `email` (unique, minúsculas),
  `passwordHash` (BCrypt), `rol` (`ADMIN`|`VIEWER`). Tabla nueva `usuario` en
  schema.sql (mismo Postgres de metadata). Sin endpoint de alta/registro en v1:
  los usuarios se crean por seed/script (ver Ambiguity Log).
- Sensor: sin cambios (los guards de FEAT-0001..0003 se mantienen; solo cambia
  cómo se autentica el request).

> Notas de implementación (no spec, no generan AC): el `RolFilter`/
> `SecurityConfig` actuales se reemplazan por verificación JWT; se agrega
> dependencia JWT pura (recomendado **jjwt 0.12.x** api/impl/jackson — librería
> Java pura, sin I/O bloqueante, cumple regla reactiva del stack) o Nimbus vía
> spring-security-oauth2-jose; `auth.jwt.secret` y `auth.jwt.expiration-seconds`
> en `application.yml` (secret con override por env `AUTH_JWT_SECRET`). Password
> hashing BCrypt (`BCryptPasswordEncoder`). Config de login expuesta como
> `application/` use case + ports (`FindUserByEmailPort`, `HashVerifier`,
> `TokenIssuer`/`TokenVerifier` ports en aplicación; adapters en infra).
