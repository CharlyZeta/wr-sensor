# CONTRACT: resiliencia del lookup de config de sensores (timeouts, circuit breaker, cache con TTL y estado observable)
# ID: FIX-0007
# Status: DRAFT
# Mode: GATE
# Gate-Mode: EXPRESS

> Origen: `docs/FIX-0007-circuit-breaker.md` (backlog), revisado en Gate. Se conserva el ID
> (próximo libre de la serie de `contracts/`). El alcance se corrigió con hallazgos verificados
> en el código: la cache existente **nunca expira** (bug de frescura) y el **token del registry
> nunca se refresca** (fallo permanente tras la expiración del JWT).

## Intent
`ingestion-service` depende de `sensor-registry` por HTTP para resolver la config de cada sensor
(`estado`, `unidadMedida`, bandas `rango*`) y hoy lo hace **sin timeout explícito, sin circuit
breaker y con una cache sin TTL**. Eso deja tres agujeros reales: (a) una respuesta colgada del
registry bloquea el lookup y el consumo del mensaje; (b) un sensor ya cacheado **jamás** se
refresca, así que si se lo desactiva o se le cambian las bandas el servicio sigue ingiriendo con
la config vieja para siempre; y (c) el token JWT que se cachea al primer login **nunca se
invalida**, de modo que al expirar (1 h, y el registry valida `exp`) todo sensor no cacheado
empieza a fallar de forma permanente hasta reiniciar el proceso. Este fix agrega **timeouts
explícitos**, un **circuit breaker reactivo propio** (cero dependencias nuevas), una **cache con
TTL y last-known-good**, el refresco del token ante `401`, un motivo de DLQ específico
(`REGISTRY_UNAVAILABLE`) y un **endpoint interno de estado**.

## Reproduction Steps
1. Levantar el stack apuntando el registry a un stub controlable:
   `INGESTION_REGISTRY_URL=http://127.0.0.1:19090` (stub que puede responder lento, fallar con 5xx
   o rechazar por token expirado) y publicar lecturas de un sensor **no cacheado** en
   `sensor.lecturas`.
2. Con el stub colgado (sin responder), medir el tiempo hasta que el mensaje termina en la DLQ y
   observar el header `x-rechazo`.
3. Publicar 10 lecturas más del mismo sensor y verificar en el stub cuántas veces fue golpeado
   (hoy: una por mensaje, sin noción de "registry caído").
4. Desactivar un sensor cuyas bandas ya están cacheadas (`DELETE /api/sensores/{id}` → `INACTIVO`,
   o `PUT` con bandas nuevas) y publicar una lectura: observar si el cambio de config se refleja.
5. Dejar el proceso corriendo más de `auth.jwt.expiration-seconds` (3600 s) y publicar una lectura
   de un sensor **no cacheado**: observar el resultado del lookup.

## Current Behavior
- Paso 2: **no hay timeout configurado**. `RegistrySensorConfigPort` construye
  `builder.baseUrl(baseUrl).build()` (sin `responseTimeout` ni connect timeout), así que el
  lookup espera el default de Netty; el mensaje termina en la DLQ con `x-rechazo: INFRA_ERROR`
  (genérico, indistinguible de un fallo de base de datos).
- Paso 3: cada mensaje vuelve a golpear el registry: no hay circuit breaker ni contador de fallos.
- Paso 4: **no se refleja nunca**. La cache es una `ConcurrentHashMap<UUID, SensorInfo>` que sólo
  se llena (`cache.put` tras el primer fetch) y **nunca se expira ni se invalida**; el chequeo
  `"INACTIVO"` de `IngestorLecturas` no ve el cambio, así que un sensor dado de baja sigue
  ingiriéndose con severidad y alertas.
- Paso 5: **falla de forma permanente**. `obtenerToken()` devuelve el token cacheado sin mirar
  `exp`, el registry valida `exp` (JwtAdapter) y responde `401`; esa respuesta no se maneja, escala
  como excepción y termina en `INFRA_ERROR` para todo sensor no cacheado, mensaje tras mensaje,
  hasta reiniciar el servicio.
- No hay ninguna forma de observar el estado: sin endpoint, sin métricas y sin logs de
  "registry caído" (sólo el WARN de rechazo por mensaje).

## Expected Behavior
- Toda llamada al registry tiene **timeout de respuesta y de conexión explícitos y configurables**
  (BR-001), nunca el default de la librería.
- Un **circuit breaker propio** (estados `CERRADO`/`ABIERTO`/`SEMIABIERTO`, umbral de fallos
  consecutivos, ventana de apertura y éxitos para cerrar) corta los llamados mientras el registry
  está caído (BR-002), y con el circuito abierto **no se toca la red** (BR-003).
- La cache tiene **TTL** y modo **last-known-good**: dentro del TTL se responde sin red; vencida,
  se refresca; si el refresh falla o el circuito está abierto y hay copia, se usa la copia con
  **WARN** (config vieja antes que perder lecturas) (BR-004). Consecuencia buscada: un sensor
  desactivado o con bandas nuevas **se ve** dentro del TTL, no nunca.
- Si no hay copia y el registry no responde, el mensaje va a la **DLQ con motivo
  `REGISTRY_UNAVAILABLE`** (no `INFRA_ERROR` genérico), sin pérdida silenciosa (BR-005).
- Un `401` del registry **invalida el token cacheado y reintenta una vez** con credenciales
  nuevas; si vuelve a fallar cuenta como fallo del circuito (BR-006). El servicio no queda en
  fallo permanente por un token vencido.
- El estado del circuito y de la cache es observable por un **endpoint interno**
  (`GET /api/ingestion/resiliencia`) más logs WARN al abrir y INFO al cerrar/semi-abrir (BR-007),
  con toda la política configurable (BR-008).

### Alternative Flows
- AF-01: token expirado (`401` en el lookup) → se descarta el token cacheado, se hace login de
  nuevo y se reintenta **una** vez; si el reintento funciona, la lectura se procesa con normalidad.
- AF-02: sensor nunca visto + circuito abierto → no hay red ni copia → DLQ
  `REGISTRY_UNAVAILABLE` (falla rápido, sin esperar timeout).
- AF-03: copia vencida + registry caído → se procesa con la copia vencida y se registra WARN con
  la antigüedad de la config (modo degradado explícito).
- AF-04: fallos esporádicos por debajo del umbral → el circuito sigue `CERRADO` y cualquier
  respuesta exitosa resetea el contador de fallos consecutivos.
- AF-05: `404` del registry (sensor inexistente) **no** es un fallo del circuito: es una respuesta
  válida (`SENSOR_UNKNOWN`), y cuenta como éxito para el breaker.
- AF-06: `SEMIABIERTO` con menos éxitos que los configurados antes de un nuevo fallo → vuelve a
  `ABIERTO` y reinicia la ventana.

## Business Rules
- BR-001: Las llamadas de `ingestion-service` a `sensor-registry` usan **timeout de respuesta**
  (default 2000 ms) y **de conexión** (default 1000 ms) explícitos y configurables
  (`ingestion.registry.timeout-ms`, `ingestion.registry.conexion-timeout-ms`). Prohibido depender
  del default de la librería. Al vencer, el lookup falla con timeout (no cuelga).
- BR-002: Existe un **circuit breaker propio** en el dominio (sin dependencias nuevas) con estados
  `CERRADO`/`ABIERTO`/`SEMIABIERTO` y política configurable: `fallos-para-abrir` (default **5**
  fallos consecutivos), `segundos-abierto` (default **30** s antes de pasar a semi-abierto) y
  `exitos-para-cerrar` (default **2** éxitos consecutivos en semi-abierto). Cuentan como fallo:
  timeout, error de conexión, `5xx` y `401` persistente tras el reintento de token. Un `404` **no**
  cuenta como fallo (AF-05).
- BR-003: Con el circuito `ABIERTO` **no se emite tráfico al registry**: se resuelve desde la
  cache (aunque la copia esté vencida) o se falla rápido con `REGISTRY_UNAVAILABLE`. El paso a
  `SEMIABIERTO` es el único que vuelve a probar la red (una llamada de sondeo).
- BR-004: La cache de config tiene **TTL configurable** (`ingestion.registry.cache.ttl-segundos`,
  default **300** s) y modo **last-known-good**: (i) copia dentro del TTL → se responde sin red;
  (ii) copia vencida → se refresca contra el registry; (iii) si el refresh falla o el circuito está
  abierto y existe copia → se usa la copia **vencida** con WARN indicando su antigüedad. Sólo se
  descarta la copia cuando no existe.
- BR-005: Si no hay copia disponible (sensor nunca resuelto) y el registry no responde, la lectura
  se rechaza con motivo **`REGISTRY_UNAVAILABLE`** y se rutea a la DLQ con ese `x-rechazo`. El
  motivo `INFRA_ERROR` queda reservado para fallos internos reales (base de datos, serialización).
- BR-006: El token del registry se cachea **con su expiración**: un `401` en el lookup invalida el
  token cacheado, fuerzan un login nuevo y reintentan **una sola vez** el lookup; si el reintento
  falla (`401` de nuevo), se cuenta un fallo del circuito y el lookup falla. Un token vencido no
  puede dejar el servicio en fallo permanente.
- BR-007: Se expone el estado por **endpoint interno** `GET /api/ingestion/resiliencia`
  (JSON: estado del circuito, fallos consecutivos, llamadas totales, tamaño y aciertos de cache,
  presencia/antigüedad del token) y por logs: **WARN** al abrir el circuito y al usar copia vencida,
  **INFO** al pasar a semi-abierto y al cerrar. Sin `actuator` ni dependencias nuevas.
- BR-008: Toda la política (timeouts, umbrales del circuito, TTL de cache) es configuración con
  defaults documentados en `application.yml` y overrides por entorno; nada hardcodeado.
- BR-009: Los **reintentos con backoff no entran** en este fix: el camino de fallo es la DLQ con
  motivo específico. `ingestion.messaging.retry-max-attempts` queda documentada como **sin uso**
  (deuda explícita) para no dejar configuración muerta sin declarar.
- BR-010: El endpoint de resiliencia es de **diagnóstico interno**: no expone datos de sensores ni
  credenciales, no agrega autenticación (el servicio no se publica: el gateway no lo enruta) y
  queda documentado como tal.
- BR-011: La resiliencia se documenta: `docs/ARQUITECTURA.md` (política y estados),
  `docs/RUNBOOK.md` (configuración, endpoint y qué hacer cuando el circuito abre),
  `docs/API.md` (motivo `REGISTRY_UNAVAILABLE`) y `docs/DECISIONES.md` (ADR-0018).

## Acceptance Criteria
- AC-001 (BR-001): GIVEN un registry stub que demora más que `timeout-ms` WHEN se resuelve un
  sensor no cacheado THEN el lookup falla por timeout en un tiempo acotado (≈ el configurado, muy
  por debajo de la demora del stub) y no queda colgado.
- AC-002 (BR-002, BR-003): GIVEN `fallos-para-abrir = 5` WHEN ocurren 5 fallos consecutivos THEN el
  circuito queda `ABIERTO` y la siguiente resolución **no golpea la red** (el stub no registra
  ninguna invocación nueva).
- AC-003 (BR-003, BR-004): GIVEN el circuito `ABIERTO` y una config previamente cacheada (aunque
  esté vencida) WHEN llega una lectura de ese sensor THEN se procesa usando la copia, sin error y
  con WARN de config vencida.
- AC-004 (BR-004): GIVEN una copia con TTL vencido y el registry operativo WHEN llega una lectura
  THEN se refresca la config (el stub registra la llamada) y **un cambio de estado se ve**: si el
  sensor pasó a `INACTIVO`, la lectura se rechaza con `SENSOR_INACTIVE` (bug de frescura corregido),
  y si las bandas cambiaron, la severidad se calcula con las nuevas.
- AC-005 (BR-004): GIVEN copia vencida y registry caído WHEN llega una lectura THEN se procesa con
  la copia vencida y se registra un WARN con su antigüedad (modo degradado, sin perder la lectura).
- AC-006 (BR-005): GIVEN un sensor nunca resuelto y el registry caído WHEN llega su lectura THEN
  termina en la DLQ con `x-rechazo = REGISTRY_UNAVAILABLE` (y no `INFRA_ERROR`).
- AC-007 (BR-006): GIVEN un token cacheado que el registry rechaza con `401` WHEN llega una lectura
  de un sensor no cacheado THEN el servicio revalida credenciales, reintenta una vez y procesa la
  lectura (no queda en fallo permanente); GIVEN que el reintento también recibe `401` THEN el
  lookup falla y cuenta como fallo del circuito.
- AC-008 (BR-002, BR-008): GIVEN un circuito `ABIERTO` WHEN transcurre `segundos-abierto` y se hace
  un sondeo exitoso THEN pasa a `SEMIABIERTO` y con `exitos-para-cerrar` éxitos consecutivos vuelve
  a `CERRADO`; todo verificado con reloj inyectado (sin esperar la ventana real).
- AC-009 (BR-007): GIVEN el circuito abriéndose y cerrándose WHEN se inspeccionan los logs THEN hay
  WARN al abrir y INFO al semi-abrir/cerrar (capturados por el test).
- AC-010 (BR-007, BR-010): GIVEN el endpoint `GET /api/ingestion/resiliencia` WHEN se consulta THEN
  devuelve el estado del circuito, los fallos consecutivos, las llamadas, el tamaño/aciertos de
  cache y la antigüedad del token; y su respuesta **no** contiene datos de sensores ni credenciales.
- AC-011 (AF-04, AF-05): GIVEN 4 fallos consecutivos y luego un éxito WHEN se resuelve otro sensor
  THEN el circuito sigue `CERRADO` y el contador quedó en 0; GIVEN un sensor inexistente (`404`)
  WHEN se resuelve THEN no cuenta como fallo y la lectura se rechaza con `SENSOR_UNKNOWN`.
- AC-012 (BR-009, BR-011): GIVEN el estado final del work item WHEN se revisan los documentos THEN
  `docs/RUNBOOK.md` explica configuración/endpoint/qué hacer con el circuito abierto,
  `docs/API.md` lista `REGISTRY_UNAVAILABLE`, `docs/ARQUITECTURA.md` describe la política y
  `docs/DECISIONES.md` registra el ADR-0018 incluyendo que `retry-max-attempts` queda sin uso.

- **DLQ**: motivo nuevo `REGISTRY_UNAVAILABLE` en `sensor.lecturas`.
- **Docs**: `ARQUITECTURA.md`, `RUNBOOK.md`, `API.md`, `DECISIONES.md` (ADR-0018), `README.md`,

## Fuera de alcance
- **Reintentos con backoff** en el consumo: el camino de fallo sigue siendo la DLQ (BR-009), y
  `messaging.retry-max-attempts` se declara sin uso en lugar de implementarla acá.
- **Cache en Redis** (o compartida entre instancias): la cache sigue siendo local al proceso; con
  FIX-0005 la afinidad sensor → partición → instancia hace que cada sensor tenga una sola instancia
  consumidora, así que una cache distribuida no aporta hoy. `stack.md` la deja prevista.
- **`actuator`/Micrometer** y métricas Prometheus: el estado se expone por endpoint propio y logs.
- **Invalidación evento-driven** de la cache (p. ej. que `sensor-registry` publique cambios de
  config): se resuelve con TTL; un bus de eventos de config sería otro contrato.
- **Circuit breaker en otras integraciones** (RabbitMQ, base de datos) y **alertas operacionales**
  cuando el circuito abre (el doc origen citaba un "FIX-0008" que no existe).
- **Autenticación del endpoint de resiliencia** (no lo enruta el gateway y no expone datos).

> Notas de implementación (no spec, no generan AC): el breaker y la política de cache son clases
> de dominio puras con reloj inyectado (mismo criterio que el token bucket de FEAT-0007); el
> `WebClient` del registry se construye con `HttpClient.create().responseTimeout(...)` y
> `CONNECT_TIMEOUT_MILLIS`, sin dependencias nuevas; el endpoint se arma con un `RouterFunction`
> (webflux ya está en el classpath porque el servicio usa `WebClient`) y se testea con
> `WebTestClient.bindToRouterFunction(...)`, sin levantar puerto. El IT usa un registry stub
> (`com.sun.net.httpserver.HttpServer`) que se puede hacer lento, fallar o responder `401`.
