# CONTRACT: Listado de sensores (GET /api/sensores) con paginación keyset
# ID: FEAT-0002
# Status: RESOLVED (Loop completado 2026-09-09 — 21/21 ítems ✅)
# Mode: LOOP (completado 2026-09-09 — todos los ítems ✅)

## Intent
Exponer `GET /api/sensores` en `sensor-registry` para listar los sensores
registrados, con paginación **keyset/cursor** (nunca `OFFSET`) y `limit`
configurable (default 100, máximo 1000). Rol permitido: `ADMIN` y `VIEWER`
(lectura — a diferencia de `POST /api/sensores` que es `ADMIN`-only en
`FEAT-0001`). Mantiene el stack reactivo (WebFlux/R2DBC) y la hexagonal de
`sensor-registry`. Fuente spec: §7 (`GET /api/sensores`, admin), §9.4
(paginación keyset, `limit` 100/1000, cursor opaco).

## Use Case
**Actor:** Usuario autenticado con rol `ADMIN` o `VIEWER`
**Goal:** Listar los sensores del sistema página a página sin degradación
(conjunto grande de años), obteniendo cada página vía un cursor opaco.

### Main Flow
1. El actor envía `GET /api/sensores` con header `Authorization` (JWT rol
   `ADMIN` o `VIEWER`); parámetros opcionales `cursor` (opaco) y `limit`.
2. El sistema valida el token y el rol (vía `RolGuard`), valida `limit` (default
   100 si ausente; rechaza con `400` si está fuera de [1, 1000]) y valida
   `cursor` (rechaza con `400` si malformado). Luego consulta el repositorio
   con paginación keyset a partir del cursor (página inicial si no hay cursor).
3. El sistema responde `200 OK` con la página de sensores y un `nextCursor`
   opaco para la siguiente página (o ausencia de cursor si no hay más).

### Alternative Flows
- AF-01: Sin header `Authorization` (o token inválido) → `401 UNAUTHENTICATED`
- AF-02: Rol del token fuera de `{ADMIN, VIEWER}` (o rol nulo) → `403 INSUFFICIENT_ROLE`.
  Nota: `VIEWER` **sí** puede listar (es lectura); el 403 aplica solo a roles ajenos al par permitido.
- AF-03: Parámetro `limit` ausente → se usa el default `100` (no es error).
- AF-04: `limit` > 1000 → `400 SENSOR_INVALID_LIMIT` (rechazo explícito; no se acota —
  consistencia con FEAT-0001 que rechaza input inválido en vez de reinterpretarlo).
- AF-05: `limit` < 1 → `400 SENSOR_INVALID_LIMIT`.
- AF-06: `limit` no numérico / no parseable → `400 SENSOR_INVALID_LIMIT`.
- AF-07: `cursor` malformado / opaco no reconocido por el servidor → `400 SENSOR_INVALID_CURSOR`.
- AF-08: `cursor` apunta al final de la colección (no hay más sensores después) → `200` sin
  `nextCursor` (fin de paginación — succès, no error).
- AF-09: No existen sensores en el sistema → `200` con lista vacía (`[]`) y sin `nextCursor`.

## Business Rules
- BR-001: Paginación **keyset/cursor**, nunca `OFFSET`. Toda consulta lista a partir de un
  cursor (o desde el inicio si no hay); `OFFSET` está prohibido en cualquier path de lectura
  del catálogo. (Invariante de stack §9.4.)
- BR-002: `limit` configurable, **default 100, máximo 1000**. Rango válido: `limit` ∈ [1, 1000].
  Fuera de rango (incluido no numérico) → `400 SENSOR_INVALID_LIMIT`.
- BR-003: `cursor` opaco para el cliente. El servidor lo genera a partir de
  `(fechaInstalacion, id)` de la última fila de la página; el cliente lo devuelve verbatim para
  pedir la siguiente. Cursor malformado / no reconocido → `400 SENSOR_INVALID_CURSOR`.
  **Sin TTL en v1** (YAGNI: no hay razón para caducidad hasta que exista requerimiento).
- BR-004: Orden determinístico **descendente por `fechaInstalacion`**, desempate **ascendente
  por `id` (UUID)**. Garantiza cursor estable y ausencia de duplicados/saltos entre páginas.
- BR-005: `nextCursor` presente en la respuesta **solo si existen más sensores después del
  último devuelto**. Última página → respuesta sin `nextCursor`.
- BR-006: Acceso de lectura permitido a `ADMIN` y `VIEWER` (diferencia de FEAT-0001: escritura
  era ADMIN-only). Rol del token fuera de `{ADMIN, VIEWER}` → `403 INSUFFICIENT_ROLE`.
- BR-007: Sin `Authorization` (o token inválido) → `401 UNAUTHENTICATED`.

## Acceptance Criteria
- AC-001: GIVEN existen ≥ 2 páginas de sensores (más de `limit` registrados) y un request
  `GET /api/sensores` con header `Authorization` con JWT rol `ADMIN` y sin `cursor`/`limit`
  WHEN el sistema procesa el request
  THEN responde `200 OK` con body conteniendo una lista de exactamente `limit` sensores
  (default 100) ordenados descendentemente por `fechaInstalacion` (desempate `id` asc),
  y un campo `nextCursor` no nulo.
- AC-002: GIVEN un request `GET /api/sensores` con header `Authorization` con JWT rol `VIEWER`
  y sin `cursor`/`limit`
  WHEN el sistema procesa el request
  THEN responde `200 OK` (mismo acceso que `ADMIN` — `VIEWER` puede listar) y body con
  la misma estructura que AC-001.
- AC-003: GIVEN el request `GET /api/sensores` no incluye header `Authorization`
  WHEN el sistema procesa el request
  THEN responde `401 UNAUTHORIZED` con body conteniendo código `UNAUTHENTICATED`.
- AC-004: GIVEN un request `GET /api/sensores` con header `Authorization` con JWT cuyo rol
  no pertenece a `{ADMIN, VIEWER}` (ej. rol `AUDITOR`)
  WHEN el sistema procesa el request
  THEN responde `403 FORBIDDEN` con body conteniendo código `INSUFFICIENT_ROLE`.
- AC-005: GIVEN existen más de 100 sensores registrados y un request `GET /api/sensores`
  con `Authorization` JWT rol `ADMIN` y `limit` ausente
  WHEN el sistema procesa el request
  THEN responde `200 OK` con body conteniendo exactamente 100 sensores (default aplicado).
- AC-006: GIVEN un request `GET /api/sensores` con `Authorization` JWT rol `ADMIN` y
  `limit=1001`
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con body conteniendo código `SENSOR_INVALID_LIMIT`.
- AC-007: GIVEN un request `GET /api/sensores` con `Authorization` JWT rol `ADMIN` y
  `limit=0`
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con body conteniendo código `SENSOR_INVALID_LIMIT`.
- AC-008: GIVEN una primera página devolvió `nextCursor` C, y un request `GET /api/sensores`
  con `Authorization` JWT rol `ADMIN` y `cursor=C`
  WHEN el sistema procesa el request
  THEN responde `200 OK` con body conteniendo la **siguiente** página: sensores cuyo
  `(fechaInstalacion, id)` es estrictamente menor al cursor decodificado por el servidor.
- AC-009: GIVEN `cursor=C` apunta al último sensor de la colección (no hay más sensores
  después) y un request `GET /api/sensores` con `Authorization` JWT rol `ADMIN` y `cursor=C`
  WHEN el sistema procesa el request
  THEN responde `200 OK` con body conteniendo una lista vacía o menor a `limit` **y sin
  campo `nextCursor`** (fin de paginación).
- AC-010: GIVEN un request `GET /api/sensores` con `Authorization` JWT rol `ADMIN` y
  `cursor="no-es-un-cursor-valido"`
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con body conteniendo código `SENSOR_INVALID_CURSOR`.
- AC-011: GIVEN no existen sensores registrados y un request `GET /api/sensores` con
  `Authorization` JWT rol `ADMIN`
  WHEN el sistema procesa el request
  THEN responde `200 OK` con body conteniendo lista vacía (`[]`) y sin `nextCursor`.
- AC-012: GIVEN existen dos sensores con igual `fechaInstalacion` y `limit` tal que el corte
  de página cae entre ambos, y un request `GET /api/sensores` con `Authorization` JWT rol
  `ADMIN` paginando con el `nextCursor` de la página anterior
  WHEN el sistema procesa el request
  THEN responde `200 OK` y **ningún sensor se duplica ni se saltea** entre páginas
  consecutivas (el desempate por `id` asegura orden total estricto).

> Nota de impl (no es spec, no genera AC): el `RolGuard` actual de FEAT-0001 expone sólo
> `requireAdmin` (hardcodea `rol != ADMIN → 403`). FEAT-0002 necesita un guard de lectura
> que permita `{ADMIN, VIEWER}` (BR-006). Es un nuevo método en `RolGuard` (ej.
> `requireReader`) — decisión de implementación del coder-agent en Loop, no de spec.

## Ambiguity Log
- [x] Cursor para listado de sensores: §9.4 define cursor=timestamp para
      lecturas (timeseries); los sensores no lo son. → RESUELTO (decisión
      humana 2026-08-12): columna de orden keyset = **`fechaInstalacion`**
      (timestamp de alta), **descendente** — los sensores más recientes
      primero. El cursor es opaco para el cliente (el servidor lo genera a
      partir del `fechaInstalacion` de la última fila de la página); el
      cliente lo devuelve tal cual para pedir la siguiente página. En caso
      de empate de `fechaInstalacion` (dos sensores con el mismo timestamp de
      alta), desempate por `id` (UUID) para orden determinístico y cursor
      estable. Fuente: campo ya existente en `Sensor` (FEAT-0001).
- [x] AF-02/AC-004 ("rol fuera de {ADMIN,VIEWER} → 403 INSUFFICIENT_ROLE")
      no era reachable con `Rol = {ADMIN, VIEWER}` de FEAT-0001: un token
      no reconocido mapeaba a `null` → 401, y el enum de 2 valores hacía
      código muerto la rama `rol != ADMIN && rol != VIEWER` del guard.
      → RESUELTO (decisión humana 2026-08-14): aprobar el **sentinel
      `Rol.OTHER`** (auth, no rol de negocio) introducido por el coder-agent
      en `domain/model/Rol.java` (comentado `ponytail:`) + `SecurityConfig.parseRol`
      que devuelve `OTHER` cuando hay header pero el rol no casa con
      ADMIN/VIEWER, y `null` solo cuando no hay header. Semántica final:
      sin header → 401 UNAUTHENTICATED; header con rol desconocido →
      403 INSUFFICIENT_ROLE; ADMIN/VIEWER → pasa. Regresión FEAT-0001
      verificada (26/26 verdes el 2026-08-14: AF04RolGuardTest 5,
      CreateSensorACTest 9, CreateSensorServiceBRTest 12) — no rompe
      el guard existente.
