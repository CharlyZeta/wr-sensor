## Intent
Exponer `PUT /api/sensores/{id}` en `sensor-registry` para editar la
**configuración de medición/alerta** de un sensor existente: rangos
(`rangoNormal`/`rangoWarning`/`rangoCritical`), `histeresis`,
`frecuenciaReporteSegundos` y `estado`. La edición aplica **solo a lecturas
futuras** (sin reproceso del histórico — decisión del Ambiguity Log FEAT-0001).
Escritura **ADMIN-only** (como POST de FEAT-0001). Fuente spec: §7
(`PUT /api/sensores`), §4 Sensor, stack.md.

## Use Case
**Actor:** Usuario autenticado con rol `ADMIN`
**Goal:** Actualizar la configuración de un sensor existente sin cambiar su identidad

### Main Flow
1. El actor envía `PUT /api/sensores/{id}` con header `Authorization` (JWT rol
   `ADMIN`) y body con la configuración editable completa.
2. El sistema valida: token/rol ADMIN (`RolGuard.requireAdmin`), `{id}` UUID
   (400 si malformado), existencia del sensor (404 si no), y las invariantes de
   configuración (rangos, histeresis, frecuencia, estado).
3. El sistema persiste los cambios (UPDATE) y responde `200 OK` con el
   `SensorResponse` **actualizado** (shape FEAT-0001/FEAT-0003).

### Alternative Flows
- AF-01: Sin `Authorization` (o token inválido) → `401 UNAUTHENTICATED`.
- AF-02: Rol del token fuera de `{ADMIN}` (VIEWER/OTHER) → `403 INSUFFICIENT_ROLE`.
- AF-03: `{id}` malformado (no UUID) → `400 SENSOR_INVALID_ID`.
- AF-04: `{id}` UUID válido inexistente → `404 SENSOR_NOT_FOUND`.
- AF-05: Validación de configuración falla (rangos no anidados, histeresis < 0,
  frecuencia fuera de rango, estado inválido o `INACTIVO` en PUT) →
  `400` con el `code` de dominio correspondiente (`SENSOR_INVALID_RANGES`,
  `SENSOR_INVALID_HISTERESIS`, `SENSOR_INVALID_FRECUENCIA`,
  `SENSOR_INVALID_ESTADO`).
- AF-06: Body con campos fuera del conjunto editable (o formato inválido en un
  campo editable) → `400 SENSOR_INVALID_REQUEST`.

## Business Rules
- BR-001: `{id}` debe ser un UUID válido; malformado → `400 SENSOR_INVALID_ID`
  (nunca 500). Precedente FEAT-0003 BR-001.
- BR-002: Editar un sensor inexistente (id UUID válido) → `404 SENSOR_NOT_FOUND`
  (nunca crear implícitamente, nunca 200).
- BR-003: La edición es **ADMIN-only** (`RolGuard.requireAdmin`): `VIEWER` y
  sentinel `OTHER` → `403 INSUFFICIENT_ROLE`; sin token/token inválido →
  `401 UNAUTHENTICATED`. (Escritura: mismo criterio que POST FEAT-0001.)
- BR-004: Conjunto **editable** = `estado` ∈ {`ACTIVO`, `MANTENIMIENTO`},
  `histeresis`, `frecuenciaReporteSegundos`, `rangoNormal`, `rangoWarning`,
  `rangoCritical`. **Inmutables** en edición: `id`, `codigo`, `nombre`, `tipo`,
  `latitud`, `longitud`, `unidadMedida`, `fechaInstalacion` (no se aceptan en el
  body; el DTO de PUT solo expone los editables).
- BR-005: El body de PUT exige la configuración editable **completa** (reemplazo
  del subset config, no merge parcial); campos faltantes o no editables →
  `400 SENSOR_INVALID_REQUEST`.
- BR-006: Las invariantes de configuración se validan con las **mismas reglas y
  codes del alta (FEAT-0001 BR-002/BR-005/BR-006)**: cadena inclusiva completa
  `critical.min ≤ warning.min ≤ normal.min ≤ normal.max ≤ warning.max ≤
  critical.max` (`SENSOR_INVALID_RANGES`); `histeresis >= 0` (0 desactiva el
  margen) (`SENSOR_INVALID_HISTERESIS`); `frecuenciaReporteSegundos` en el rango
  del alta (`SENSOR_INVALID_FRECUENCIA`).
- BR-007: En v1 el PUT **no** permite `estado=INACTIVO` (la baja lógica con su
  semántica — chequeos, evento — es FEAT-0005). Enviar `INACTIVO` →
  `400 SENSOR_INVALID_ESTADO`.
- BR-008: La edición **no reprocesa lecturas históricas**: solo actualiza la fila
  `sensor`; las lecturas nuevas (futuras) usarán la configuración vigente al
  momento de evaluarse (invariante de alcance; el reproceso no existe en v1).

## Acceptance Criteria
- AC-001: GIVEN existe un sensor ACTIVO con rangos/histéresis/frecuencia
  conocidos, y un request `PUT /api/sensores/{id}` con JWT rol `ADMIN` y body
  válido que cambia `histeresis` a `1.0` y `rangoNormal` a {min:3, max:7}
  WHEN el sistema procesa el request
  THEN responde `200 OK` con el `SensorResponse` conteniendo `histeresis=1.0`,
  `rangoNormal={min:3,max:7}` y el resto de atributos intactos (`id`, `codigo`,
  `estado`, rangos warning/critical).
- AC-002: GIVEN el mismo escenario y un request con JWT rol `VIEWER`
  WHEN el sistema procesa el request
  THEN responde `403 FORBIDDEN` con code `INSUFFICIENT_ROLE` (la edición es
  ADMIN-only, a diferencia de la lectura).
- AC-003: GIVEN un request `PUT /api/sensores/{id}` sin header `Authorization`
  WHEN el sistema procesa el request
  THEN responde `401 UNAUTHORIZED` con code `UNAUTHENTICATED`.
- AC-004: GIVEN un request `PUT /api/sensores/{id-inexistente}` (UUID válido) con
  JWT rol `ADMIN` y body válido
  WHEN el sistema procesa el request
  THEN responde `404 NOT FOUND` con code `SENSOR_NOT_FOUND`.
- AC-005: GIVEN un request `PUT /api/sensores/no-es-un-uuid` con JWT rol `ADMIN`
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con code `SENSOR_INVALID_ID`.
- AC-006: GIVEN un request con `histeresis = -0.5` (resto válido)
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con code `SENSOR_INVALID_HISTERESIS`.
- AC-007: GIVEN un request con rangos que rompen la cadena inclusiva (p. ej.
  `rangoCritical={min:5,max:9}` con `rangoWarning={min:2,max:6}`)
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con code `SENSOR_INVALID_RANGES`.
- AC-008: GIVEN un request con `estado = INACTIVO` (resto válido)
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` con code `SENSOR_INVALID_ESTADO`
  (INACTIVO solo vía baja lógica FEAT-0005).
- AC-009: GIVEN un request que omite un campo editable obligatorio (p. ej. sin
  `rangoWarning`) o incluye un campo inmutable (p. ej. `codigo`)
  WHEN el sistema procesa el request
  THEN responde `400 BAD REQUEST` — con el code de dominio del campo faltante
  (criterio estructural del alta FEAT-0001: `rangoWarning` → `SENSOR_INVALID_RANGES`)
  o `SENSOR_INVALID_REQUEST` cuando el body incluye un campo no editable/ilegible.

## Entities Affected
- Sensor (owner=sensor-registry): **update** de `estado` (ACTIVO/MANTENIMIENTO),
  `histeresis`, `frecuenciaReporteSegundos` y los tres rangos. Identidad
  (`id`, `codigo`, `nombre`, `tipo`, `latitud`, `longitud`, `unidadMedida`,
  `fechaInstalacion`) inmutable. Reutiliza las invariantes de configuración de
  FEAT-0001. Sin columna ni entidad nueva.

> Notas de implementación (no spec, no generan AC): requiere port out de update
> (`UpdateSensorPort` → `Mono<Sensor>` del estado persistido actualizado) y el
> caso de uso `UpdateSensorUseCase/Service` que valida el subset editable con las
> mismas reglas que el alta (extraer/compartir validadores de configuración).
> El endpoint PUT reutiliza `RolGuard.requireAdmin`, `SensorResponse` y el path
> `/{id}` (parseo UUID igual que FEAT-0003). Para rechazar campos inmutables
> (AC-009): DTO con `@JsonIgnoreProperties(ignoreUnknown = false)` y
> `GlobalErrorHandler` mapeando `HttpMessageNotReadableException` →
> `400 SENSOR_INVALID_REQUEST` (mismo body code que los demás errores).

## Ambiguity Log
- [x] Alcance de campos editables: RESUELTO (humano 2026-09-09) = **solo configuración de
      medición/alerta** (`estado`, `histeresis`, `frecuenciaReporteSegundos`,
      rangos); `nombre` y demás identidad quedan inmutables en v1. Alternativa =
      permitir editar también `nombre`. Requiere decisión humana.
- [x] `estado=INACTIVO` en PUT: RESUELTO (humano 2026-09-09) = **rechazarlo** (la baja lógica con su
      semántica es FEAT-0005). Alternativa = permitirlo ahora (deja a FEAT-0005
      solo como DELETE semántico). Requiere decisión humana.
- [x] Evento de dominio al editar: RESUELTO (humano 2026-09-09) = **sin evento `sensor.updated` en
      v1** (YAGNI: no hay consumidores aún; FEAT-0011 definirá los contratos de
      mensajería de lecturas). Alternativa = publicar `sensor.updated`
      (consistencia con `sensor.created` de FEAT-0001). Requiere decisión humana.
- [x] Semántica del body: RESUELTO (humano 2026-09-09) = **PUT con subset config completo
      obligatorio** (reemplazo; sin merge parcial). Alternativa = permitir PATCH
      parcial (solo campos presentes). Requiere decisión humana (menor).
