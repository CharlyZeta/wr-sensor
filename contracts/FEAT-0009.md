## Intent
El backend está completo —login, CRUD, histórico, última lectura, resumen del mapa, WS de lecturas y
de alertas, todo detrás del punto de entrada único con CORS y WS autenticado (`FEAT-0008`)— pero **no
existe frontend**: hoy la única forma de ver los sensores es `curl`. Este work item crea la **base
del SPA** (andamiaje, sesión con JWT, layout y cliente API con el manejo correcto de los errores y del
cupo del gateway) y entrega la primera pantalla con valor real: el **mapa de sensores** alimentado
por `GET /api/sensores/resumen` (una sola request, `FEAT-0008`), con los sensores coloreados por
severidad y navegables al detalle. Además cierra el **hosting**: el SPA se sirve desde el gateway
(mismo origen, sin CORS en producción) sin romper el `404 ROUTE_NOT_FOUND` de la API.
Lo que queda fuera —detalle en vivo con WS, feed de alertas, CRUD y simulador— son las partes 2, 3 y 4.

## Use Case
**Actor:** operador con rol `ADMIN` o `VIEWER` (credenciales de `sensor-registry`).
**Goal:** entrar con su usuario y ver de un golpe **dónde está cada sensor y en qué estado está**,
con la sesión, el cupo y los errores del backend manejados de forma explícita, desde una única URL
(el gateway) y sin instalar nada.

### Main Flow
1. El usuario abre el SPA en `http://<gateway>/` (en producción lo sirve el gateway; en desarrollo
   Vite en `http://localhost:5173` contra el gateway con `GATEWAY_CORS_ORIGENES` configurado). Sin
   sesión activa, el SPA muestra la pantalla de **login**.
2. Ingresa credenciales y el SPA hace `POST /api/auth/login` (mismo origen) → recibe
   `{token, rol, expiraEnSegundos}`, guarda la sesión y navega al **mapa**.
3. El SPA pide `GET /api/sensores/resumen` y dibuja **un marcador por sensor** en su
   `latitud`/`longitud`, coloreado por la `severidad` de su última lectura (gris si
   `ultimaLectura` es `null`), y lista los mismos sensores al costado con su valor y hora.
4. Click en un marcador o en la lista → navega a `/sensores/{id}`, que muestra la metadata del
   sensor y su última lectura conocida (el detalle en vivo por WS llega en `FEAT-0014`).
5. El SPA refresca el resumen con el período configurado, muestra el estado de la conexión y de la
   última actualización, y expone el `X-Correlation-Id` de la última response para soporte.
6. El usuario cierra sesión (o el token expira) → el SPA vuelve al login y no deja datos del
   usuario anterior en pantalla.

### Alternative Flows
- AF-01: token ausente o expirado → **una** petición devuelve `401 UNAUTHENTICATED`; el SPA cierra la
  sesión, avisa y muestra el login (sin bucle de reintentos ni pantalla rota).
- AF-02: rol sin permiso (`403 INSUFFICIENT_ROLE`) → mensaje de "sin permisos para esta acción" y la
  sesión sigue viva.
- AF-03: cupo agotado (`429 RATE_LIMIT_EXCEEDED` con `Retry-After`) → aviso no bloqueante con cuenta
  atrás, **un** reintento automático al vencer y suspensión del refresco periódico mientras dure.
- AF-04: el registry no responde (`502 REGISTRY_UNAVAILABLE`, `FEAT-0008` AF-06) → el mapa muestra un
  estado de error con botón "reintentar" y **nunca** marcadores parciales presentados como completos.
- AF-05: gateway caído, error de red o `5xx` inesperado → estado de error con reintento, y los datos
  en pantalla quedan marcados como **no actualizados desde <hora>** (nunca se muestran como frescos).
- AF-06: sesión de `VIEWER` → las acciones de escritura y el panel de administración **no se
  ofrecen** (no se muestran botones que el backend va a rechazar).
- AF-07: el usuario entra a una URL de cliente (p. ej. `/sensores/abc`, `/mapa`) → el gateway
  devuelve el índice del SPA y el router del cliente resuelve la ruta.
- AF-08: el resumen viene **vacío** (no hay sensores) → estado vacío explícito con la acción
  disponible según el rol, nunca un mapa en blanco sin explicación.
- AF-09: los tiles del mapa no cargan (sin red al CDN) → la app sigue siendo usable: marcadores y
  lista sobre fondo neutro, con aviso de que el mapa base no está disponible.

## Business Rules
- BR-001: **El SPA se sirve desde el gateway (mismo origen).** El build del SPA se publica como
  recursos estáticos del gateway (`services/api-gateway/src/main/resources/static/`, **generado en el
  empaquetado y no versionado**) y el *fallback* de rutas del cliente se aplica **sólo** a paths que
  no son de API: todo `/api/**` no declarado sigue respondiendo `404 ROUTE_NOT_FOUND` (BR-008 de
  `FEAT-0007`) y `/ws/**` sigue exigiendo upgrade con token (`FEAT-0008` BR-003). Con esto la lista
  `gateway.cors.origenes` puede quedar **vacía** en producción.
- BR-002: **El token se guarda en `sessionStorage`** (sobrevive al F5, se borra al cerrar la
  pestaña). Nunca en `localStorage`, nunca en una cookie (el backend no emite cookies de sesión) y
  nunca en la URL. Ver Ambiguity Log.
- BR-003: **Todo el tráfico sale por el mismo origen**: las URLs del backend son relativas
  (`/api/...`, `/ws/...`) con base configurable por build (`VITE_API_BASE`, vacía por default).
  Ningún host/URL de backend queda hardcodeado en el bundle.
- BR-004: **Los errores se muestran por `code`**, con un diccionario `code → mensaje es-AR`; el
  status HTTP y el `X-Correlation-Id` se muestran en el detalle técnico (para soporte), nunca como
  mensaje principal. Un `code` desconocido se muestra tal cual (no se inventa un texto).
- BR-005: **Se respeta el rate limiting del gateway**: el refresco del resumen usa el período
  configurado (`VITE_RESUMEN_REFRESCO_MS`, default 30 s — 2 requests/min por pestaña, muy por debajo
  del cupo de la clase `lectura` de 120/min), nunca hay polling por debajo de eso, y ante `429` se
  espera el `Retry-After` recibido.
- BR-006: **El mapa es Leaflet** (decisión humana 2026-09-14) con la capa de tiles configurable
  (`VITE_TILES_URL`); la app **no depende** de los tiles para ser usable (marcadores + lista).
- BR-007: **Una sola fuente de verdad para la severidad** (`severidad → color` + `calidad`): el mismo
  mapeo lo usan marcador, lista y leyenda; `NORMAL`/`WARNING`/`CRITICAL` con la paleta accesible, y
  un sensor sin lecturas se distingue **sin depender sólo del color** (forma/ícono/etiqueta) —
  requisito de accesibilidad, no estético.
- BR-008: **Toda vista tiene estado de carga, error y vacío** (nunca pantalla en blanco) y los textos
  están en **es-AR** centralizados en un único diccionario. La UI es navegable por teclado y cumple
  contraste AA en los colores de severidad.
- BR-009: **El estado global es mínimo**: sesión en un contexto propio + datos por ruta con hooks
  propios. No se agrega librería de estado ni de data-fetching sin decisión explícita en el
  Ambiguity Log.
- BR-010: **El frontend se construye y testea en su propio pipeline**: `npm ci` (con
  `package-lock.json` **versionado**), `npm test` y `npm run build`; el resultado se copia a los
  recursos estáticos del gateway en el empaquetado (stage de Node en la imagen Docker del gateway y
  comando documentado para local; la carpeta generada **no** se versiona). El build del SPA
  **requiere red** (registry npm): no se integra al ciclo `mvn -o` del backend ni lo rompe.
- BR-011: **Documentado y configurable**: `docs/RUNBOOK.md` (correr el SPA en dev y en prod, variables
  `VITE_*`, cómo se testea), `docs/ARQUITECTURA.md` (estructura del frontend + hosting/empaquetado,
  sin romper el 404 de la API), `README.md` y un **ADR nuevo** con las decisiones de stack del SPA.
  Ningún valor nuevo hardcodeado: nada de puertos, orígenes ni tiles en el código.

## Acceptance Criteria
- AC-001 (BR-001): GIVEN el stack levantado WHEN se pide `GET /` al gateway THEN responde `200`
  `text/html` con el índice del SPA, y `GET /api/loquesea` sigue respondiendo
  `404 ROUTE_NOT_FOUND`.
- AC-002 (BR-001, AF-07): GIVEN una ruta de cliente (`/sensores/abc`) WHEN se pide al gateway THEN
  responde `200` con el índice (el router del SPA la resuelve), mientras `/api/sensores/abc` sigue
  llegando al registry.
- AC-003 (Main Flow 2/3): GIVEN credenciales válidas WHEN el usuario hace login THEN el SPA muestra
  el mapa con un marcador por cada sensor del resumen y el rol queda reflejado en la UI.
- AC-004 (BR-007): GIVEN un resumen con severidades `NORMAL`, `WARNING`, `CRITICAL` y un sensor con
  `ultimaLectura: null` WHEN se pinta el mapa THEN cada marcador/ítem usa el color y la etiqueta
  esperados y el sensor sin lecturas se distingue también sin color.
- AC-005 (BR-004, AF-04): GIVEN que el backend responde `502 REGISTRY_UNAVAILABLE` WHEN se carga el
  mapa THEN se muestra el mensaje asociado a ese `code` con el `X-Correlation-Id` en el detalle
  técnico y el botón de reintento, y no hay marcadores en pantalla.
- AC-006 (BR-002, AF-01): GIVEN un token vencido WHEN el SPA pide el resumen THEN cierra la sesión,
  muestra el login y, tras re-loguear, vuelve a la ruta que el usuario había pedido.
- AC-007 (BR-005, AF-03): GIVEN una respuesta `429` con `Retry-After: 5` WHEN el SPA reintenta THEN
  espera al menos ese tiempo, muestra un aviso no bloqueante y no dispara una ráfaga de reintentos.
- AC-008 (AF-08, BR-008): GIVEN un resumen vacío y GIVEN una pantalla en carga WHEN se renderiza
  THEN se ve el estado vacío/carga correspondiente con texto en español y ninguna pantalla en blanco.
- AC-009 (AF-09, BR-006): GIVEN que la capa de tiles no responde WHEN se abre el mapa THEN los
  marcadores y la lista siguen operativos (click y navegación funcionan) y se informa que el mapa
  base no está disponible.
- AC-010 (BR-010): GIVEN el repositorio WHEN se corre el pipeline del frontend (`npm ci`, `npm test`,
  `npm run build`) THEN pasa en verde y el build queda publicado en los recursos del gateway.
- AC-011 (BR-011, AF-06): GIVEN los documentos y la configuración WHEN se revisan THEN RUNBOOK,
  ARQUITECTURA y el ADR describen cómo se corre/sirve el SPA y sus variables, y ningún archivo fuente
  contiene URLs de backend, puertos ni tiles hardcodeados.
