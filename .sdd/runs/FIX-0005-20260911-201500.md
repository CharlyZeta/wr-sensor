- **Decision Rationale**:

     agregarlo cambiaría el publisher (viola BR-002 del doc original) → los AC se apoyan en

     introduce **afinidad sensor → partición → instancia** en lugar de mover el estado.
  3. El particionamiento se resuelve en el broker (consistent hash) para no tocar el
     publisher; requiere habilitar el plugin, tanto en compose como en los ITs.
  4. Un consumer por partición con `qos = 1` y `concatMap` materializa BR-002 (orden
     intra-partición); las particiones corren en paralelo entre sí.
  5. Si la topología no se puede declarar, se registra ERROR y no se consume: nunca se
     degrada en silencio a "consumir sin particionar" (BR-009).
  6. Rechazo: se publica en la DLQ y recién después se asienta (ack), comportamiento vigente
     de FEAT-0011 que evita el loop de poison message (cubierto en AC-005).

## Incidencias de ejecución (intentos fallidos y corrección)
1. `subscribe(suscripciones::add)` y `Flux.merge(List)` no compilaban (tipos `Void`/`Object`)
   → `Disposable consumo = ...subscribe()` + `Flux.fromIterable(colas).flatMap(...)`.
2. `Mono.fromRunnable` infería `Object` dentro de `concatMap` → `Mono.<Void>fromRunnable(...)`.
3. Test BR-002 (paralelismo): el decremento de "en vuelo" en `doFinally` ocurría *después*
   de propagar el `onComplete`, así que `concatMap` ya había pedido el siguiente elemento y el
   contador marcaba 2 → el decremento se movió al `Supplier` que produce el resultado.
4. Test AF-04: el cuerpo usaba un timestamp fijo de 2026-09-11 y la ventana temporal
   (`ventanaSegundos=300`) lo rechazaba → el timestamp pasa a ser `Instant.now()`.
5. Test BR-006: se afirmaba "nunca ack" tras un rechazo, pero el comportamiento contratado
   (FEAT-0011) es publicar en la DLQ y luego asentar → se corrigió la aserción.
6. `FIX0005DocsTest`: aserción de substring mal formada (`data-simulator`)** **no`) →
   corregida contra el texto real del documento.
7. IT AC-005: el `basicGet` con autoAck dentro del predicado consumía el mensaje antes de la
   aserción → se guarda el `GetResponse` en un `AtomicReference`.
8. IT AC-006: `Instancia solo` no era effectively final dentro del lambda → copia final.
9. IT (7 errores en la primera corrida): `queuePurge` sobre una cola inexistente provoca
   reply-code 404 y **cierra el canal AMQP** → el `setUp` quedaba con el canal muerto; se
   purga con canales descartables.
10. IT AC-003/AC-004: la management API de RabbitMQ **omite los campos en cero**, así que
    "0 consumers / 0 mensajes" llegaba como campo ausente y se interpretaba -1 → el parser
    ahora trata ausencia como 0 y los chequeos de "0 consumers" esperan a que se propague la
    cancelación de los consumers de la corrida previa.
11. IT AC-003: el `declare` es asíncrono (Reactor RabbitMQ) → las aserciones de topología
    esperan a que las colas existan antes de leer la API.
